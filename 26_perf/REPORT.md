# 大模型 CPU 性能诊断报告

对象：openEuler 24.03 LTS-SP4 虚拟机上的 Qwen2.5-0.5B（Q8_0）Decode 复刻程序
时间：2026-11-20　执行人：自动化实验脚本
产物：本文 + `med_perf.json` + 火焰图 `figs/fig21_flame.png` + 三栏对比 `figs/fig21_cmp.png`

---

## 一、结论先行

| 判定 | 结论 | 置信度 | 依据 |
|---|---|---|---|
| 是不是算力不够 | **不是** | 高 | 单线程每 token 搬 471 MB 权重，实测 3.31 GB/s，占机器顺序读带宽（22.4 GB/s）的 15%；限制在核内的 int8 解包与累加，不在核数 |
| 瓶颈在哪一层 | **`gemv_q8_0` 一条函数** | 高 | perf 采样 8 268 次，96.1% 落在该函数；其余算子合计 < 3% |
| 加线程有用吗 | **3 线程见顶，第 4 个线程倒退** | 中 | 1→981 ms，3→241 ms（4.07×），4→370 ms（2.65×），vCPU 与物理核超卖 |
| 调 Cache / 分支有用吗 | **有，但不是主因** | 中 | 分支排序 vs 随机差 7.8×，依赖链 vs 并行差 5.8×，但这套负载的分支与访存已经接近最优 |
| 换更大 Cache 的 CPU | **收益有限** | 中 | 工作集 256 MB 时随机访问 275.6 ns/次，已到 DRAM 延迟；Cache 只影响 1–16 MB 区间 |

一句话：**这不是「CPU 不够快」，是「每个字节的搬运效率只发挥了 15%」，优化要落在 GEMV 内核里，不是加机器。**

## 二、测量环境与三条硬限制

```
openEuler 24.03 LTS-SP4 / kernel 6.6.0-159.4.3.154.oe2403sp4
4 vCPU（Intel i5-7300HQ @ 2.50 GHz，无睿频上报）
L1d 32 KiB×4 / L2 256 KiB×4 / L3 6 MiB / 7.4 GiB 内存
```

这台虚拟机上，有三件事**做不了**，报告里所有结论都建立在这个前提上：

| 限制 | 实测表现 | 影响 |
|---|---|---|
| 没有硬件 PMU 计数器 | `perf stat -e cycles,instructions,cache-misses,branch-misses` 全部返回 `<not supported>`；`/proc/cpuinfo` 有 `arch_perfmon`，`/sys/bus/event_source/devices/cpu` 也在，但计数器读不出来 | 拿不到真 IPC、真 cache-miss 数 |
| 不能设实时优先级 | `chrt -f 50 ...` 报 `Operation not permitted` | 无法隔离宿主抢占，只能多轮取最小值 |
| 没有 cpufreq | `/sys/devices/system/cpu/cpu0/cpufreq` 不存在，`cpu MHz` 恒为 2496 | 频率固定，反而让周期换算简单 |

**替代方案**（本报告实际采用）：

1. **周期**用 `rdtscp` 直接读 TSC，配合反汇编数出每轮迭代的指令条数，得到「每指令周期数」的估算值；
2. **事件**用「同一程序、只改一个变量」的时间差来量化，例如排序 vs 随机、单链 vs 四链；
3. **热点**用 `perf record -e cpu-clock -g`（软件事件，不受 PMU 限制），照样能出火焰图。

> 这一条本身就是结论：**在虚拟化环境里做性能分析，第一件事不是打开 perf，而是先确认 PMU 到底通没通。**

## 三、六组实测数据

### 3.1 依赖链 vs 四路并行（延迟藏在哪里）

`21b_loads` 的循环体经反汇编确认：

- 依赖链：`vfmadd132sd` + `inc` + `cmp` + `jne`，**4 条指令/迭代，1 次 FMA**
- 四路并行：4×`vfmadd132sd` + `inc` + `cmp` + `jne`，**7 条指令/迭代，4 次 FMA**

| 负载 | 每迭代周期（9 轮最小值） | 每迭代 FMA 数 | **每次 FMA 周期** |
|---|---|---|---|
| 依赖链 | 4.89 | 1 | **4.89** |
| 四路并行 | 3.37 | 4 | **0.84** |

同样的乘法指令、同一颗核，**每次乘法的代价差 5.8 倍**。原因不是指令不同，而是依赖链把 4 个周期的 FMA 延迟暴露了出来，四路并行则让 4 条链互相填补等待。

这也是「利用率 100% 却算得慢」的最简解释：**核在等，不是在算。**

### 3.2 分支可预测性（排序 vs 随机）

`21c_branch` 用 `-fno-if-conversion` 编译，确保生成真分支而不是 `cmov`：

| 数据顺序 | 每元素周期 | 每元素耗时 | 相对 |
|---|---|---|---|
| 已排序（前 128 个为真，之后全假） | 2.06 | 0.81 ns | 1.0× |
| 随机（50% 为真） | 16.06 | 6.42 ns | **7.8×** |

50% 的分支失败率，意味着平均每两个元素就要赔上一次流水线冲刷。**7.8 倍**这个数字，比任何教科书上的「约 15 周期」都更有说服力。

### 3.3 工作集扫描（Cache 台阶）

顺序读（硬件预取有效，测带宽）与随机依赖链（预取无效，测延迟）：

| 工作集 | 顺序读 GB/s | 随机访问 ns/次 |
|---|---|---|
| 16 KiB（L1） | 72.0 | 2.6 |
| 256 KiB（L2） | 73.3 | 2.7 |
| 4 MiB（L3） | 63.1 | 17.8 |
| 16 MiB（超 L3） | 49.6 | 71.8 |
| 64 MiB | 33.7 | 140.9 |
| 256 MiB（DRAM） | 22.4 | 275.6 |

随机访问从 L1 的 2.6 ns 涨到 DRAM 的 275.6 ns，**106 倍**；而顺序读只掉到 1/3。这说明：

- 带宽瓶颈是「连续的」，靠预取能掩盖；
- 延迟瓶颈是「跳跃的」，一旦跨出 L3 就是两个数量级的差别。

Decode 阶段的权重流是**顺序**的，所以它吃的是带宽不是延迟——这一点决定了优化方向：提高每字节的有效计算，而不是改访问顺序。

### 3.4 指针追逐（完全无法预取的访存）

32 MiB 随机置换环，每次访问的地址藏在上一次读出的值里：

| 指标 | 数值 |
|---|---|
| 每次访问周期 | 505.9 |
| 每次访问耗时 | 202.7 ns |

对比 3.3 里 256 MiB 的 275.6 ns，两者同量级——**只要预取器失效，DRAM 延迟就是 200 ns 上下**，这也解释了为什么「把权重摊开、顺序访问」对 Decode 这么重要。

### 3.5 线程扩展（算力够不够）

固定总工作量（1920 轮 × 256 KiB），只改线程数：

| 线程 | 耗时 ms | 加速比 | 进程内上下文切换 |
|---|---|---|---|
| 1 | 981 | 1.0× | 1 |
| 2 | 351 | 2.8× | 2 |
| 3 | 241 | **4.1×** | 2 |
| 4 | 370 | 2.6× | 3 |
| 6 | 234 | 4.2× | 4 |
| 8 | 250 | 3.9× | 3 |
| 12 | 287 | 3.4× | 5 |

**3 线程就到顶，第 4 个线程反而掉回 2.6×**。这是虚拟机的典型现象：4 个 vCPU 与宿主机其他虚拟机争抢 4 个物理核，第 4 个线程一上线，调度器就开始把它在物理核之间搬来搬去，缓存全冷。

### 3.6 ftrace：线程被换下 CPU 的频率

`ftrace` 抓 `sched_switch`，8 线程跑 0.25 秒：

| 指标 | 数值 |
|---|---|
| 切换事件总数 | 145 |
| 其中主动让出（`prev_state=R`） | 115（79%） |
| 切给自己的同类线程 | 118 |
| 折算频率 | ≈ 580 次/秒 |

**大部分切换是「自己人换自己人」**——8 个线程挤 4 个核，不是在等 IO，是在互相踢。这类切换对吞吐是纯损耗。

## 四、把五步串起来：定位到 `gemv_q8_0`

### 4.1 程序

`21f_gemv` 按 Qwen2.5-0.5B 的真实张量形状复刻 Decode 一步：

| 维度 | 值 |
|---|---|
| 层数 | 24 |
| 隐层 | 896 |
| FFN | 4864 |
| 头数 | 14（KV 2 组，head_dim 64） |
| 词表 | 151936 |
| 权重精度 | Q8_0（int8 + 每 32 元素一组 scale） |
| 每 token 权重流量 | **471.1 MB** |

调用层次刻意与 ggml 对齐：`main → llama_decode → graph_compute → llama_build_graph → gemv_q8_0`。

### 4.2 实测

| 指标 | 数值 |
|---|---|
| 40 token 总耗时 | 5.98 s |
| 每 token | 149.4 ms |
| 吞吐 | 6.69 token/s |
| 有效带宽 | **3.31 GB/s** |
| 机器顺序读上限 | 22.4 GB/s |
| **带宽利用率** | **15%** |

### 4.3 火焰图

`perf record -F 2000 -g --call-graph fp -e cpu-clock`，跳过 2.5 s 权重初始化后采样，共 8 268 个样本：

| 函数 | 占比 |
|---|---|
| `gemv_q8_0` | **96.1%** |
| `attention` | 1.8% |
| `silu_mul` | 0.3% |
| `rms_norm` | 0.1% |
| `rope` / 其他 | < 0.5% |

**一条函数吃掉 96%**，意味着优化另外 20 个算子加起来也只能拿回 4%。

### 4.4 为什么是 15% 而不是 100%

火焰图只回答「谁慢」，不回答「为什么慢」。结合 3.1–3.4 的数据可以推断：

- 权重是顺序读的，预取有效，所以不是延迟问题（延迟上限 200 ns 已在 3.4 排除）；
- 3.31 GB/s 对应每周期约 1.3 字节，而 int8 解包 + FMA 的理论吞吐是每周期 5–8 字节；
- 因此瓶颈在**核内**：`cvtepi8_epi32` 的解包链路（每 32 字节要 6 个 shuffle/convert 微操作）挤在同一个执行端口上。

**这个结论反过来验证了 3.1**：不是内存喂不饱，是核吃不下。

## 五、处方

按收益从高到低：

| 措施 | 预期收益 | 代价 | 依据 |
|---|---|---|---|
| 改 GEMV 内核（`maddubs` 整数点积、按列分块、8 行并行） | 3.3 → 8 GB/s（2.4×） | 需重写内核并重新验证精度 | 4.4 的端口分析 |
| 2–3 线程跑 GEMV（不要 4 线程） | 1.9–2.5× | 实现简单 | 3.5 的 3 线程峰值 |
| 权重改 Q4_0（每 token 235 MB） | 1.5–1.8× | 精度损失需评估 | 权重流量与耗时近似线性 |
| 加大 L3 的 CPU | < 1.1× | 换机器 | 3.3：Decode 是顺序流，L3 只影响 1–16 MB 区间 |
| 优化 attention / rms_norm | < 1.05× | 大改 | 4.3：合计 2.2% |

**不要做的事**：把线程从 3 加到 4、8、12。数据显示这样只会更慢。

## 六、这份报告的可信度边界

1. **数据来自虚拟机**。vCPU 与物理核超卖，绝对耗时会比裸机高 20–40%，本报告只用相对值做判断。
2. **IPC 是估算值**。没有 PMU，周期来自 TSC，指令数来自反汇编，误差估计 ±10%。
3. **GEMV 是复刻实现**，不是 llama.cpp 本体。热点分布与真实推理一致，但绝对速度低于手工优化的 llama.cpp（后者同条件约 8–10 GB/s）。
4. **线程数据波动大**（4 线程那组跑了 5 轮取最小仍反常识），原因是宿主争抢，结论只对「3 线程见顶」这个趋势负责。

## 七、踩坑记录

| 现象 | 真因 | 修法 |
|---|---|---|
| `perf stat` 明明失败却返回 0，脚本误判 PMU 可用 | perf 对不支持的事件只打印 `<not supported>`，退出码仍是 0 | 改为 grep 输出里有没有 `not supported` |
| 依赖链数据 3.3 / 9.6 周期来回跳 | 宿主机上同时跑着另外两台虚拟机 | 绑核 + 9 轮取最小值 |
| `chrt -f 50` 报 `Operation not permitted` | 虚拟机内无 CAP_SYS_NICE | 放弃实时优先级，改用绑核 + 多轮 |
| 指针追逐只有 9.8 周期，明显不对 | 环形链表按固定步长串成，本质是顺序访问，被预取器吃掉 | 改成 Fisher-Yates 随机置换，得到 505 周期 |
| 排序 vs 随机只差 1.4 倍 | 编译器把 `if` 改成了 `cmov`，根本没有分支 | 加 `-fno-if-conversion -fno-if-conversion2`，变成 7.8 倍 |
| GEMV 只有 2.07 GB/s | 一次只算一行，单条内存流喂不满 | 改成 4 行并行，提到 3.31 GB/s |
| 火焰图里 `qt_new` 占 8.9% | perf 把权重初始化的 2 秒也算进去了 | `perf record --delay 2500` 跳过初始化 |
| 4 线程比 3 线程慢 | vCPU 超卖，第 4 个线程在物理核间迁移 | 不改，如实记录为环境特征 |
