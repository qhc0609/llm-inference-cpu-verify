# 大模型 CPU 性能诊断报告

对象：openEuler 24.03 LTS-SP4 虚拟机上的 Qwen2.5-0.5B（Q8_0）Decode 复刻程序
时间：2026-11-20　执行人：自动化实验脚本
产物：本文 + `med_perf2.json` + 火焰图 `figs/fig21_flame.png` + 三栏对比 `figs/fig21_cmp.png`

> 本版为**第二版**。第一版有三处度量错误（顺序读带宽虚高 3 倍、线程加速比用脏分母、周期数当固定频率换算），
> 已全部推翻重测。第六节列出哪些数据作废、为什么作废。

---

## 一、结论先行

| 判定 | 结论 | 置信度 | 依据 |
|---|---|---|---|
| 是不是算力不够 | **不是** | 高 | 单线程每 token 搬 471 MB 权重，实测 3.15 GB/s，占机器顺序读带宽（15.6 GB/s）的 20%；瓶颈在核内 int8 解包，不在核数 |
| 瓶颈在哪一层 | **`gemv_q8_0` 一条函数** | 高 | perf 采样 8 268 次，96.1% 落在该函数；其余算子合计 < 3% |
| 加线程有用吗 | **4 线程用满物理核，再加无收益** | 高 | 有效并行度 1.0 → 1.9 → 2.8 → **3.4（4 线程）**，6/8 线程停在 3.5–3.6，墙钟不再下降 |
| 调 Cache / 分支有用吗 | **有，但不是主因** | 中 | 分支排序 vs 随机差 7.8×，依赖链 vs 并行差 5.3×，但这套负载的分支与访存已接近最优 |
| 换更大 Cache 的 CPU | **收益有限** | 中 | 顺序读从 L1 的 24.0 GB/s 只掉到 DRAM 的 15.6 GB/s（1.5×），预取把这些都掩盖了 |

一句话：**这不是「CPU 不够快」，是「每个字节的搬运效率只发挥了 20%」，优化要落在 GEMV 内核里，不是加机器。**

## 二、测量环境与四条硬限制

```
openEuler 24.03 LTS-SP4 / kernel 6.6.0-159.4.3.154.oe2403sp4
4 vCPU（Intel i5-7300HQ @ 2.50 GHz）
L1d 32 KiB×4 / L2 256 KiB×4 / L3 6 MiB / 7.4 GiB 内存
```

| 限制 | 实测表现 | 影响 |
|---|---|---|
| 没有硬件 PMU | `perf stat -e cycles,instructions,cache-misses,branch-misses` 全部 `<not supported>`；`arch_perfmon` 标志在、设备节点也在，但计数器读不出来。vmx 里加 `vpmu.enable="TRUE"` 重启后依旧无效 | 拿不到真 IPC、真 cache-miss 数 |
| **读不到核心频率** | `/sys/devices/system/cpu/cpu0/cpufreq` 不存在，`cpu MHz` 永远是 2496 | **周期数只能按固定 2.5 GHz 换算，而核的实际频率在变**——这是本报告最大的不确定性来源 |
| 不能设实时优先级 | `chrt -f 50 ...` 报 `Operation not permitted` | 无法隔离宿主抢占，只能多轮取最优 |
| vCPU 不独占物理核 | 有效并行度峰值只有 3.4–3.6（见 3.5） | 4 个 vCPU 里约半个被宿主机拿走 |

**替代方案**：

1. **周期**用 `rdtscp` 读 TSC，指令数用反汇编数，两者相除得估算 IPC；绝对值不可靠，只用于同机横向比较；
2. **不信任单一时刻的数**：每档连测 7 轮，报「范围 + 中位」；
3. **加一个抗频率干扰的指标**：`CPU 时间 ÷ 墙钟` = 有效并行度，同一时段内计算，频率漂移被约掉；
4. **热点**用 `perf record -e cpu-clock -g`（软件事件，不受 PMU 限制）。

> 这一条本身就是结论：**在虚拟化环境里做性能分析，第一件事不是打开 perf，而是先确认 PMU 通没通、频率稳不稳。**

## 三、六组实测数据

### 3.1 依赖链 vs 四路并行（延迟藏在哪里）

`21b_loads` 的循环体经反汇编确认：

- 依赖链：`vfmadd132sd` + `inc` + `cmp` + `jne`，**1 次 FMA/迭代**
- 四路并行：4×`vfmadd132sd` + `inc` + `cmp` + `jne`，**4 次 FMA/迭代**

| 负载 | 每次 FMA 周期（7 轮范围） | 中位 |
|---|---|---|
| 依赖链 | 4.88 ~ 11.18 | 10.40 |
| 四路并行 | 0.84 ~ 3.01 | 1.97 |
| **同轮相除** | **2.8 ~ 8.0 倍** | **5.3 倍** |

范围宽是因为频率在飘（同一段代码连跑 7 轮，TSC 换算出的周期数差 2.3 倍）。但两档是**同一轮里挨着跑**的，频率飘的时候一起飘，所以**比值**稳得住：5.3 倍。

原因不是指令不同，是依赖链把 4–5 周期的 FMA 延迟暴露了出来，四路并行让 4 条链互相填补等待。这也是「利用率 100% 却算得慢」的最简解释：**核在等，不是在算。**

### 3.2 分支可预测性（排序 vs 随机）

`21c_branch` 用 `-fno-if-conversion` 编译，确保生成真分支而不是 `cmov`：

| 数据顺序 | 每元素周期 | 每元素耗时 | 相对 |
|---|---|---|---|
| 已排序（前段全真，之后全假） | 2.06 | 0.81 ns | 1.0× |
| 随机（50% 为真） | 16.06 | 6.42 ns | **7.8×** |

50% 的分支失败率，意味着平均每两个元素就要赔上一次流水线冲刷。这一组 7 轮抖动只有 9%，是本报告**最稳**的数据之一。

### 3.3 工作集扫描（Cache 台阶）

顺序读（预取有效，测带宽）与随机依赖链（预取无效，测延迟）：

| 工作集 | 顺序读 GB/s | 随机访问 ns/次 |
|---|---|---|
| 16 KiB（L1） | 24.0 | 4.2 |
| 256 KiB（L2） | 24.6 | 4.7 |
| 4 MiB（L3） | 20.3 | 19.3 |
| 16 MiB（超 L3） | 16.0 | 77.5 |
| 64 MiB | 17.0 | 124.5 |
| 256 MiB（DRAM） | **15.6** | **268.2** |

随机访问从 4.2 ns 涨到 268.2 ns，**64 倍**；顺序读只从 24.0 掉到 15.6，**1.5 倍**。这说明：

- 带宽瓶颈是「连续的」，靠预取能掩盖；
- 延迟瓶颈是「跳跃的」，一旦跨出 L3 就是两个数量级的差别。

Decode 阶段的权重流是**顺序**的，所以它吃的是带宽不是延迟——优化方向是提高每字节的有效计算，而不是改访问顺序。

> 第一版这几个数是 72 / 73 / 63 / 50 / 34 / 22.4，全部虚高约 3 倍。原因是代码把「一遍的耗时」当成「三遍的总量」来换算。修正后 15.6 GB/s 正好落在 DDR4-2400 单通道的理论值附近。

### 3.4 指针追逐（完全无法预取的访存）

32 MiB 随机置换环，每次访问的地址藏在上一次读出的值里：

| 指标 | 数值 |
|---|---|
| 每次访问周期 | 505.9 |
| 每次访问耗时 | 202.7 ns |

对比 3.3 里 256 MiB 的 268.2 ns，两者同量级——**只要预取器失效，DRAM 延迟就是 200–270 ns 上下**。

### 3.5 线程扩展（几个核在真干活）

固定总工作量（1920 轮 × 256 KiB），只改线程数，每档测 7 轮：

| 线程 | 墙钟中位 | **有效并行度（中位 / 峰值）** | 读法 |
|---|---|---|---|
| 1 | 1971 ms | 0.9 / 1.0 | 单线程，一个核 |
| 2 | 744 ms | 1.8 / 1.9 | 接近 2 个核 |
| 3 | 337 ms | 2.5 / 2.8 | 约 2.5 个核 |
| 4 | 333 ms | 2.6 / **3.4** | 逼近 4 核上限 |
| 6 | 320 ms | 2.7 / 3.6 | 线程多了，核没多 |
| 8 | 323 ms | 3.2 / 3.5 | 峰值停在 3.5 |

**给 8 个线程，也只有 3.5 个核在干活。** 线程数早就够了，卡在物理核上——4 个 vCPU 里还有半个被宿主机拿走。

> 第一版这里的结论是「3 线程见顶、第 4 个线程掉到 2.65×」。那是**错的**：用墙钟算加速比时，单线程那一次恰好撞上低频，分母被抬高，比值就虚了（甚至算出 6.7×，超过 4 核上限）。改用有效并行度后，真实图景是「加到 4 线程用满物理核，之后不再增长」。

### 3.6 ftrace：线程被换下 CPU 的频率

`ftrace` 抓 `sched_switch`，8 线程跑 0.25 秒：

| 指标 | 数值 |
|---|---|
| 切换事件总数 | 145 |
| 其中被抢占换下（`prev_state=R`） | 115（79%） |
| 换上来仍是同类线程 | 118 |
| 折算频率 | ≈ 580 次/秒 |

**大部分切换是「自己人换自己人」**——8 个线程挤 4 个核，不是在等 IO，是在互相踢。这类切换对吞吐是纯损耗，和 3.5 的「峰值停在 3.5 核」是同一件事的两个观测面。

## 四、把五步串起来：定位到 `gemv_q8_0`

### 4.1 程序

`21f_gemv` 按 Qwen2.5-0.5B 的真实张量形状复刻 Decode 一步：

| 维度 | 值 |
|---|---|
| 层数 | 24 |
| 隐层 | 896 |
| FFN | 4864 |
| 头数 | 14（KV 2 组，head_dim 64） |
| 词表 | 151936 |
| 权重精度 | Q8_0（int8 + 每 32 元素一组 scale） |
| 每 token 权重流量 | **471.1 MB** |

调用层次刻意与 ggml 对齐：`main → graph_compute → llama_build_graph → gemv_q8_0`。

### 4.2 实测

| 指标 | 数值 |
|---|---|
| 每 token（5 轮中位） | **149.7 ms**（范围 143.6 ~ 159.4） |
| 吞吐 | 6.68 token/s |
| 有效带宽 | **3.15 GB/s** |
| 机器顺序读上限 | 15.6 GB/s |
| **带宽利用率** | **20%** |

5 轮抖动 11%，说明这一组比周期类指标稳定得多（它测的是长时间的字节流量，不依赖单次频率状态）。

### 4.3 火焰图

`perf record -F 2000 -g --call-graph fp -e cpu-clock --delay 2500`，跳过 2.5 s 权重初始化后采样，共 8 268 个样本：

| 函数 | 占比 |
|---|---|
| `gemv_q8_0` | **96.1%** |
| `attention` | 1.8% |
| `silu_mul` | 0.3% |
| `rms_norm` | 0.1% |
| `rope` / 其他 | < 0.5% |

**一条函数吃掉 96%**，意味着优化另外 20 个算子加起来也只能拿回 4%。火焰图是采样占比，不依赖频率，所以这一条在两版报告里都成立。

### 4.4 为什么是 20% 而不是 100%

火焰图只回答「谁慢」，不回答「为什么慢」。结合 3.1–3.4 可以推断：

- 权重是顺序读的，预取有效，所以不是延迟问题（延迟上限 270 ns 已在 3.3 排除）；
- 3.15 GB/s 对应每周期约 1.3 字节，而 int8 解包 + FMA 的理论吞吐是每周期 5–8 字节；
- 因此瓶颈在**核内**：`cvtepi8_epi32` 的解包链路（每 32 字节要 6 个 shuffle/convert 微操作）挤在同一个执行端口上。

**这个结论反过来验证了 3.1**：不是内存喂不饱，是核吃不下。

## 五、处方

按收益从高到低：

| 措施 | 预期收益 | 代价 | 依据 |
|---|---|---|---|
| 改 GEMV 内核（`maddubs` 整数点积、按列分块、8 行并行） | 3.15 → 8 GB/s（2.5×） | 需重写内核并重新验证精度 | 4.4 的端口分析 |
| 用 4 线程跑 GEMV，**不要超过 4** | 2–3× | 实现简单 | 3.5：4 线程有效并行度 3.4，6/8 线程不再提升 |
| 权重改 Q4_0（每 token 235 MB） | 1.5–1.8× | 精度损失需评估 | 权重流量与耗时近似线性 |
| 加大 L3 的 CPU | < 1.1× | 换机器 | 3.3：Decode 是顺序流，L1→DRAM 只差 1.5 倍 |
| 优化 attention / rms_norm | < 1.05× | 大改 | 4.3：合计 2.2% |

**不要做的事**：把线程加到 6 个以上。3.5 显示墙钟从 333 ms 只降到 320/323 ms，有效并行度不再上升，多出来的只是切换开销。

## 六、这份报告的可信度边界

**能站住的**（抖动 < 15%，且不依赖频率换算）：

| 数据 | 抖动 | 为什么可信 |
|---|---|---|
| 顺序读带宽曲线 | < 1%（小工作集） | 长时间字节流量，取多轮最优 |
| 分支 7.8× | 9% | 两组各 9 轮，比值稳定 |
| 随机延迟 268 ns | 8% | 依赖链，天然串行，难被干扰 |
| 火焰图 96.1% | 采样占比 | 只统计样本分布，与频率无关 |
| 有效并行度 | — | 同时段内 CPU 时间/墙钟，频率漂移自动抵消 |

**要打折的**：

1. **周期数只能给范围**。虚拟机读不到核心频率，TSC 按固定 2.5 GHz 换算，同一代码连跑 7 轮能差 2.3 倍。本报告一律写「范围 + 中位」，不给单点值。
2. **有效并行度峰值 3.5，不是 4**。宿主机在抢，所以任何「加速比」都只能当趋势看，不能当绝对值。
3. **GEMV 是复刻实现**，不是 llama.cpp 本体。热点分布与真实推理一致，但绝对速度低于手工优化的 llama.cpp（后者同条件约 8–10 GB/s）。
4. **单线程基线本身受频率影响**。3.5 里单线程墙钟从 1126 到 2234 ms 都有，所以那张表刻意不报加速比。

## 七、踩坑记录（含第二版新增）

| 现象 | 真因 | 修法 |
|---|---|---|
| `perf stat` 明明失败却返回 0 | perf 对不支持的事件只打印 `<not supported>`，退出码仍是 0 | 改 grep 输出里有没有 `not supported` |
| `chrt -f 50` 报 `Operation not permitted` | 虚拟机内无 CAP_SYS_NICE | 放弃实时优先级，改绑核 + 多轮 |
| 指针追逐只有 9.8 周期 | 环形链表按固定步长串成，本质是顺序访问，被预取器吃掉 | 改 Fisher-Yates 随机置换，得 505 周期 |
| 排序 vs 随机只差 1.4 倍 | 编译器把 `if` 改成 `cmov`，根本没有分支 | 加 `-fno-if-conversion -fno-if-conversion2`，变 7.8 倍 |
| GEMV 只有 2.07 GB/s | 一次只算一行，单条内存流喂不满 | 改 4 行并行，提到 3.15 GB/s |
| 火焰图里 `qt_new` 占 8.9% | perf 把权重初始化的 2 秒也算进去了 | `perf record --delay 2500` 跳过初始化 |
| **同一段 FMA 循环，周期数从 4.88 跳到 11.18** | TSC 按固定 2.5 GHz 走，核的实际频率在变；`cpufreq` 不存在，读不到真实值 | 改报范围 + 中位，并用「同轮相除」消掉频率项 |
| **顺序读带宽报出 72 GB/s，比 DDR4 理论值高 3 倍** | 代码把「一遍的耗时」当「三遍的总量」算带宽 | 修正公式为 `bytes / 单遍耗时`，得 24.0 / 15.6 |
| **4 核跑出 6.7× 加速比** | 加速比的分母（单线程）恰好撞上低频，被抬高一倍 | 改用有效并行度 `CPU时间÷墙钟`，得 3.4–3.6 |
| **「3 线程见顶、第 4 线程掉下来」** | 同一批脏数据推出的假象，取中位数后结论直接反转 | 用交叉轮转（每轮把所有档跑一遍）+ 有效并行度重测，改成「4 线程用满」 |
