CPU 功耗与温控优化：怎么让大模型在端侧连续跑八小时不掉速

2026-11-23 复测 · 系列第 24 篇 · 实验环境：Ubuntu 22.04 / 8 vCPU 云实例（Xeon Platinum 8369B） · 配套代码与原始输出：https://github.com/qhc0609/llm-inference-cpu-verify/tree/main/29_power_thermal

一台没有风扇、没有温度传感器、连频率都读不到的机器，是怎么被判出「它没有在降频」的？

这一篇要解决的问题很具体：大模型在端侧跑久了会变慢，到底是 CPU 热了在降频，还是别的什么东西在抢时间？这两种情况的优化手段完全相反——一个要改散热和调频策略，一个要改 CPU 隔离和配额。而在这台虚拟机上，频率、温度、功耗三个数一个都读不到。所以这一篇除了讲原理，更重要的是讲一套「读不到也能判」的方法，以及七组实验把这个方法验证一遍。

一、先把一个误解拆掉：让 CPU 发烫的不是「算得多」

很多人以为，大模型推理费电是因为「算得多」。于是第一反应是换更强的 CPU、或者把乘法器做得更宽。这个直觉在训练上大致成立，在推理上基本是错的。

解码阶段每生成一个 token，CPU 要把整个权重矩阵过一遍。以 7B 模型、FP16 权重为例，一个 token 要读约 14 GB 的数据，而真正做的乘加只有约 70 亿次。算一下比例：每读 1 字节，只做 0.25 次乘加。这个数叫算术强度（arithmetic intensity），它是判断「算力瓶颈还是带宽瓶颈」的第一把尺子。

阶段每 token 的数据量每 token 的乘加算术强度瓶颈在哪
decode（逐字生成）≈ 全部权重（7B FP16 ≈ 14 GB）≈ 70 亿次0.25 FLOP/字节内存带宽
prefill（读完整段提示词）权重 + 中间激活随提示词长度平方增长几十到上百 FLOP/字节算力
CPU 的算力带宽比——约 20~50 FLOP/字节两者差两个数量级

算术强度 = 乘加次数 ÷ 读取字节数。它远低于 CPU 的算力带宽比时，乘法器大部分时间在等数据。

打个比方：你请了一位刀工极好的厨师（算力），但配菜员每次只递一根葱（带宽）。厨师一秒能切一百刀，可一秒只拿到一根葱，于是他的时间全花在伸手等葱上。这时候把刀磨得更快没用，得把配菜的路修宽。

这就是为什么 CPU 在推理时功耗看起来很「高」：核心一直处于 100% 占用，但里面大部分晶体管在等内存，真正在翻腾的是缓存、内存控制器和互连总线。这些部件不上班也不行——它们必须持续搬运，频率一降，搬运就更慢，于是「降频省电」和「照常供电」之间就出现了一个需要仔细权衡的区间。

二、一颗 CPU 的功耗，分成两块

芯片的功耗从来不是一个数，而是两块加起来：动态功耗和静态功耗。前者是晶体管翻转时给电容充放电花掉的钱，后者是不翻转时也在漏掉的电。

动态功耗 Pdyn = α · C · V² · f　　静态功耗 Pstatic = V · Ileak(T)

符号含义工程上怎么动它
α翻转率（activity factor），单位时间内有多少门真的在翻转减少无用计算、关掉空闲单元（时钟门控）
C等效电容，跟工艺和走线有关换工艺、减少长走线；软件改不了
V供电电压降压（往往和降频绑定，见下一节）
f时钟频率调频，这是软件最直接的旋钮
Ileak漏电流，随温度指数上升降温；温度越高漏得越多，形成正反馈

αCV²f 里电压是平方项，所以「降一点压」比「降一点频」省得多。

静态功耗那一条最容易被忽略，但它决定了「热失控」是否存在。漏电流随温度大致按指数上升，温度每升 10 ℃，漏电可能涨一倍。漏电涨了，功耗涨，温度再涨——这就是为什么手机烫到一定程度会突然「雪崩式」掉帧：不是调度器慌了，而是再不管就要烧穿了。

内核视角

内核里能干预的只有 α 和 f 两个量：f 走 cpufreq，α 走「别让空闲的核空转」。V 和 C 属于硅片和板级，内核碰不到——除了通过 OPP 表间接选择「哪一档电压配哪一档频率」。这也是为什么调功耗的第一步永远是「少干活」，第二步才是「降频」。

三、DVFS：为什么降 20% 的频率，能省掉近一半的电

DVFS（Dynamic Voltage and Frequency Scaling，动态电压频率调节）的核心不是「降频」，而是「频率和电压一起降」。原因在半导体的一条经验规律：一颗芯片能跑多高的频率，取决于供电电压；频率越高，需要的电压越高，且大致线性。

相对频率需要的相对电压相对动态功耗（V²f）相对性能
100%100%100%100%
90%约 95%约 81%90%
80%约 90%约 65%80%
70%约 85%约 51%70%
50%约 75%约 28%50%

电压线性、功耗平方、性能线性——这就是 DVFS 的「立方红利」：功耗按频率的三次方掉，性能只按一次方掉。

把这张表读成一句话：跑到 70% 的频率，只花 51% 的功耗，性能还剩 70%。能效（性能 ÷ 功耗）从 1.00 涨到 1.37。这就是为什么几乎所有移动设备都不愿意长期跑最高频——最高频那一段的边际能效极差。

但这条红利有个前提：任务真的是「算力受限」。回到第一节的结论，decode 是带宽受限的——频率降了，内存控制器的频率往往不跟着降（它有自己的档位），于是性能可能只掉一点点，而核心功耗掉一大截。这也是端侧跑大模型时，「适度限频」经常比「全速跑」更划算的原因。

反直觉的地方

在这台虚拟机上，我测到的恰恰是反过来的：频率读不到、温度读不到，唯一能观测的是「每 token 花了多少 CPU 时间」。后面第十节会用这个代理指标把「真降频」和「被别的进程抢走时间」区分开——这两个现象在 tokens/s 上长得一模一样。

四、Linux 的 CPUFreq 子系统：一个目录就是全部接口

在 Linux 上，调频这件事被抽象得非常规整：每个 CPU 在 sysfs 里有一个 cpufreq 目录，里面全是纯文本文件。写文件就是下命令，读文件就是看状态。

文件读它得到什么写它能干什么
scaling_driver这层频是谁在管（intel_pstate / acpi-cpufreq / rockchip-cpufreq）只读
scaling_available_governors支持哪些调频策略只读
scaling_governor当前用的是哪个策略写入策略名即可切换
scaling_min_freq / scaling_max_freq策略允许的频率上下限写入 kHz 值，夹住可用区间
scaling_cur_freq策略「想要」的频率只读
cpuinfo_cur_freq硬件「实际」的频率只读，某些平台不支持
scaling_available_frequencies这块芯片支持的所有档位只读

scaling_cur_freq 和 cpuinfo_cur_freq 经常不一样：前者是软件的目标值，后者是硬件回报值，排查「降频没生效」时要看后者。

这四层结构值得记一下，因为出问题时你需要在四层之间逐层排除：策略（governor）决定要多少频，核心层（cpufreq core）负责把请求翻译成 OPP（Operating Performance Point，一档「频率+电压」组合），驱动（driver）负责真正写寄存器，硬件最后决定给不给。

内核视角

cpufreq core 用一个 notifier 链把「频率要变了」这件事广播出去：CPU 热插拔、时间基准（clocksource）、调度器的容量感知（capacity）都会挂在这个链上。所以你在用户态改一次 scaling_max_freq，内核里跟着动的远不止频率寄存器——调度器对「这颗核有多强」的判断也会同步更新，这也是后面绑核、限频能影响调度决策的原因。

听起来很完备。那这台虚拟机上是什么样？我先把接口摸了一遍，结果是空的——这件事本身值得单独说，因为它决定了后面所有实验只能怎么做。

接口正常物理机上这台虚拟机上
/sys/devices/system/cpu/cpu0/cpufreq一整个目录，七八个可读写文件目录不存在
/sys/class/thermal/thermal_zone*每个传感器一个 zone，含 temp 与 trip_point_*一个都没有
/sys/class/thermal/cooling_device*风扇、限频器等降温手段只有 4 个 type=Processor 的占位，没绑 zone
/sys/class/powercapRAPL 能耗计数器（energy_uj）空目录
MSR 0x198（当前频率比）读出真实 P-state 比例四个核全读回 0
perf cycles / instructions硬件性能计数器

这张表不是凑数：它解释了为什么这一篇的实验必须绕道——频率、温度、瓦数三个数，在这台机器上没有一个能直接读。

五、调频策略：同样一档频率，谁来决定「该跑多快」

governor 是 cpufreq 里的「决策者」。它每隔一小段时间看一次负载，决定下一段该跑哪一档频率。同一个频率档位，用不同 governor，省电和响应速度能差出一倍。

governor决策依据特点适合什么场景
performance永远最高频响应最快、最费电、最热压测、延迟敏感且不在乎电
powersave永远最低频最省电，性能可能腰斩待机、后台轻负载
ondemand负载超过阈值就拉满，掉下来再降老牌，频率跳变剧烈老内核、桌面
conservative像 ondemand，但一档一档地爬平滑，爬升慢笔记本省电
schedutil直接用调度器的负载信号（PELT）与调度同源，最贴合实际需求现代内核默认
userspace用户态写什么就是什么完全手动实验、固定频率压测

schedutil 之所以成为默认，是因为它不再「猜」负载，而是直接问调度器：这个 CPU 上排队的任务需要多少算力。

为什么 schedutil 更准？因为调度器本来就知道每个任务有多「重」（PELT 的 util 值），也知道有几个任务在等。ondemand 只能看「上一段时间 CPU 有多忙」，——一个每 10 毫秒醒来干 1 毫秒的活，ondemand 会以为是满载，schedutil 知道它其实只要 10% 的算力。

内核视角

PELT（Per-Entity Load Tracking）给每个调度实体维护一个指数衰减的平均利用率，半衰期 32 毫秒。schedutil 拿这个值除以 CPU 的 capacity（capacity 又受 cpufreq 影响，形成闭环），算出目标频率。所以「改频率上限」不只是省电，还会通过 capacity 改变调度器对任务摆放的判断——这两件事在内核里是耦合的。

还有一个容易被忽略的角色：boost。任务刚被唤醒的那一瞬间，PELT 的平均值还很低，schedutil 会给出一个偏低的频率，于是「点亮屏幕」「按下发送」这类突发操作会觉得卡。为此内核提供了 util clamp（uclamp）和 boost 机制，允许短时间抬高频率。这也解释了为什么「平均功耗」和「手感」经常对不上：功耗看的是长期平均，手感看的是那几十毫秒的尖峰。

六、温度是怎么被读到的：thermal zone 与 trip point

温度不是「一个」数，而是「一堆」数。一颗 SoC 上通常有十几个温度传感器：每个大核一个、GPU 一个、内存控制器一个、充电芯片一个。内核把它们统一抽象成 thermal zone，每个 zone 有一个当前温度和一串阈值（trip point）。

接口含义典型用法
/sys/class/thermal/thermal_zoneN/type这个 zone 是谁（cpu-thermal、gpu-thermal…）确认传感器归属
.../temp当前温度，单位 0.001 ℃（读出来 65000 就是 65 ℃）采集、画曲线
.../trip_point_M_temp第 M 个阈值温度看系统打算在几度动手
.../trip_point_M_type阈值类型：passive / active / critical区分「降频」和「关机」
.../policy这个 zone 用哪种降温策略step_wise / power_allocator
/sys/class/thermal/cooling_deviceN/cur_state降温手段当前档位看风扇转速或限频档

trip point 分三类：passive 触发降频，active 触发风扇，critical 直接关机。热管理说到底就是在这些阈值之间做选择。

以一颗手机 SoC 为例，厂商通常会在 60 ℃ 设第一个 passive 阈值（开始轻度限频）、75 ℃ 设第二个（明显限频）、95 ℃ 设 critical（强制关机保护）。这些数字不是拍脑袋定的：硅片的长期可靠性对温度极敏感，结温每高 10 ℃，某些失效模式的寿命就减半。

这台机器上的实情

我在这台虚拟机上找不到任何一个 thermal_zone：/sys/class/thermal 下只有 cooling_device0~3，type 全是 Processor，但没有对应的 zone 去驱动它们。原因不复杂——温度传感器是主板上的物理器件，虚拟化层默认不把它直通给 guest。所以「测温度」这条路在这里是死的，不是我偷懒。

七、Thermal Framework：温度高了，谁来按下减速键

thermal framework 的结构可以概括成一条链：传感器（thermal zone）→ 阈值（trip point）→ 降温手段（cooling device）。中间那个「怎么降」的策略，就是 thermal governor。

策略思路优点缺点
step_wise超过阈值就一档一档往上加降温力度实现简单、行为可预测反应慢，容易在阈值附近抖
power_allocator（IPA）把「整机功率预算」按需求分给 CPU/GPU能效最优，现代手机默认需要准确的功率模型
fair_share各降温设备平均分摊简单不考虑谁更有效
bang_bang过阈值就全开、下来就全关极端简单震荡明显

IPA（Intelligent Power Allocation）是现在的主流：它不盯温度，而是盯「还剩多少功率预算」，把预算按需分配。

把 cpufreq 注册成 cooling device 是关键一步：这样 thermal 就不用自己管频率，只需要说「降两档」，cpufreq 负责落地。于是你会看到同一个 scaling_max_freq 被两个方向改写——用户态写、thermal 也写，谁最后写谁生效。这也是「明明我设了最高频，跑一会儿又掉下来」的常见原因。

内核视角

thermal 与 cpufreq 之间通过 cooling device 的 cur_state 交互，而 cpufreq 的 cooling 实现是「把 max_freq 压到某个档位」。所以排查顺序应该是：先看 thermal_zone 的 temp 与 trip，再看 cooling_device 的 cur_state 有没有被拉高，最后才怀疑 governor。跳过前两步直接改 governor，通常会白忙一场。

八、长时间跑大模型，究竟会发生什么

把一台没做过热设计的机器拿来连续跑推理，典型曲线是这样的三段：前几十秒是「冲刺期」，频率能顶到 turbo（比如 2.5 GHz 的基频冲到 3.1 GHz）；接着进入「平台期」，封装功耗撞上 PL1 上限，频率回落到基频附近；如果散热跟不上，结温继续爬，撞到 trip point，thermal 开始限频，进入「衰减期」，这时候 tokens/s 会明显掉。

阶段持续时间频率tokens/s 表现谁在起作用
冲刺期几十秒turbo，高于基频最高，且平稳硬件自动超频
平台期数分钟回落到基频附近略降，基本平稳PL1/PL2 功耗墙
衰减期取决于散热被 thermal 一档档压低持续下降，抖动变大thermal + cpufreq
恢复期数十秒到数分钟负载撤掉后回升—温度回落，限制解除

端侧设备最怕的是第三段：用户感知不到「为什么刚才快现在慢」，只会觉得「这东西越用越卡」。

更麻烦的是，这三段在「tokens/s」这一个指标上，和「别的进程抢了 CPU」长得几乎一样。要区分它们，必须再看一个量：每个 token 花了多少 CPU 时间。

现象tokens/s每 token 的 CPU 时间说明
真降频下降上升同样的活要更多时间，频率掉了
被抢 CPU下降基本不变活还是那么快，只是没轮到它
换了更重的模型下降上升每次要搬的数据变多了
缓存命中变差下降上升（幅度小）同样字节数，等内存的时间变长

这张表是这一篇最有用的一张：只有把「墙钟时间」和「CPU 时间」放在一起看，才能把四种原因分开。

九、性能、功耗、温度：三个数不可能同时最优

工程师最常问的一句话是「能不能又快又省又不烫」。答案是：可以接近，但不能同时取极值。因为这三者被同一组物理量绑在一起：频率高 → 性能好、功耗大、温度高；频率低 → 反过来。你能做的是在约束下找最优点，而不是消灭约束。

目标手段代价适合
延迟最低performance + 不绑核 + 高并发功耗和温度都顶格，长期会降频短时压测、离线批处理
能效最高限频到能效拐点 + schedutil + 绑核单请求延迟变差端侧常驻服务
最稳定留一颗核 + 限最大频 + 控制并发峰值性能放弃一部分车载、工业设备
最省电powersave + 深度 idle响应慢，可能错过实时性待机、传感器节点

真实产品通常是「稳定优先」：宁可峰值低一点，也要保证跑八小时不掉速。

端侧还有一个特殊约束：散热是被动。手机、车机、开发板都没有风扇，热量只能靠外壳和空气。这意味着「持续性能」几乎完全由结构决定，软件能做的只有「别让热量集中在同一颗核上」——这正好接回第二十三篇讲的绑核与隔离。

一句话总结这一节：功耗优化的目标不是「把频率压低」，而是「在给定的散热条件下，让每一焦耳换到最多的 token」。前者是手段，后者才是目的。

十、工程实验：让模型连着跑四分钟，然后盯着三个数

前面九节讲的是原理。原理讲完，最要紧的一步是：在一台真实机器上，把「模型持续跑」这件事做出来，然后把性能、功耗、温度三个方向的变化记下来。这一节就是这件事的记录。

实验在 Ubuntu 虚拟机上做，内核 6.8.0-149-generic，4 个 vCPU，宿主是一台 Intel Xeon 服务器。测试程序是一个「按解码阶段特征写的假模型」：每一轮把 32 MB 的权重矩阵从内存完整读一遍，读的过程中做乘加，读完整一遍算生成一个 token。它不快，也不聪明，但它和真模型干的是同一件事——把权重从内存搬到寄存器，顺便乘一下。所以它的 token 速度、每 token 的 CPU 时间、随负载变化的规律，都是可以迁移到真模型上的。

10.2 温度读不到，那就换一个能读的量：每 token 的 CPU 时间

问题变成：有没有一个量，既能反映「CPU 变慢了」，又不需要任何特权接口？有，而且很朴素——每个 token 花了多少 CPU 时间。

推理程序在每生成一个 token 的前后各读一次 getrusage(RUSAGE_THREAD)，两次相减就是这个 token 真正占用 CPU 的时长（不含被换出去等待的时间）。把所有 token 的这个值排个序，取第 10 百分位，记作 p10。

为什么取 p10 而不是平均？因为一个 token 的 CPU 时间会被很多东西污染：被宿主机抢走一段、缓存刚好被换掉、页表刚好要补。这些污染都只会让时间变长，不会让它变短。所以「最快的那 10% 的 token」恰好代表了没有干扰时的真实速度，而平均值把这堆干扰全算进来了。

打个比方：你要测一条路最快能开多快。别看「今天所有车的平均到达时间」——那里面混着堵车、下雨、有人找车位。看「今天最顺的那几趟」，那个时间只由路本身决定。p10 就是「最顺的那几趟」。

这个量的好处是：它和频率严格成反比。频率掉 30%，同样的活就要多花 43% 的 CPU 时间。于是「p10 有没有持续上升」这个问题，等价于「频率有没有持续下降」。温度读不到没关系，降频的后果是能读到的。

现象每秒 token 数每 token 的 CPU 时间（p10）结论
真降频下降上升频率掉了，同样的活要更多时间
CPU 被别人抢下降基本不变活还是那么快，只是分到的时间少了
换成更重的模型下降上升每次要搬的数据变多了
缓存命中变差下降上升（幅度小）字节数没变，等内存的时间变长

这张判别表是整篇的方法论核心：单看吞吐会被骗，必须把「墙钟时间」和「CPU 时间」放在一起看。

3.91 倍，四个核对四个线程，效率 97.8%。这就是「资源给足」时这套负载该有的样子。

为什么上一版只有 2.24 倍，这一版接近线性？差别不在代码，在芯片的两项参数：

参数上一版：i5-7300HQ这一版：Xeon 8369B对这套负载的意义
L3 容量6 MB48 MB32 MB 权重在 Xeon 上装得进 L3，四线程读的是同一份缓存；在 i5 上装不下，四条流全落到内存
内存通道双通道 DDR4-2400（≈38 GB/s 理论）8 通道 DDR4-3200（≈205 GB/s 理论）四线程同时流式读时，Xeon 的带宽余量是 i5 的 5 倍以上
物理核数4 核 4 线程（无 SMT）32 核 64 线程（配额 8）钉 4 个物理核不会撞到超线程兄弟

上一版把 2.24 倍解释成「四个线程抢同一份内存带宽」，这个解释在 i5 上是对的：6 MB 的 L3 装不下 32 MB 权重，四个线程各自流式读，很快就撞死在双通道内存上。这一次同样的代码、同样的权重，48 MB 的 L3 把整个权重装进去了，于是四个线程从「抢带宽」变成了「各自算」，加核就几乎线性。

所以「4 核只快 2.24 倍」不是这条负载的固有属性，而是那颗芯片的算力带宽比。这也修正了上一版一个容易外推的结论：当时写「加核能加算力，加不了带宽，所以四个线程挤在一起谁也跑不满」——这句话只在 L3 装不下权重时成立。一旦权重大小落在 L3 之内，加核就是加算力。

把这条接到端侧：判断「要不要多开线程」的正确顺序是先看权重能不能进末级缓存，再看内存通道数，最后才看核数。反过来做——先上多线程再发现没加速——就是上一版踩过的坑。

这和上一版形成了最直接的反差：笔记本上四轮是 92.4 → 99.3 → 86.5 → 74.8，最后一轮掉了 19%，每 token 时间从 34.2 ms 涨到 40.7 ms，两个数一起坏。当时只能写「观察到劣化，但无法归因到温度」。这一次连劣化的影子都没有。

原因不神秘。这台机器的 CPU 时间由宿主的 cgroup 配额统一调度，散热也由宿主管——本容器无论跑多久，看到的都是同一份算力。只要 8 vCPU 配额没被别人抢走，就不会出现「跑热了变慢」这种形态；真出现变慢，也只会以「被限流」的形式出现，而那是 10.7 要拆的事。

一句必须说的边界：「四轮没劣化」不等于「真机不会热降频」。它只说明在这台云实例上、这四分钟里，没有可观测的累积成本。要论证热降频，必须有温度或频率读数，而这台机器一条都没有。

10.7 第四组：用「同核竞争」做一次份额对照

前面所有推断都建立在一个假设上：「每秒 token 数下降」可以由「分到的时间变少」引起，而「每 token 的 CPU 时间不变」。这个假设如果不验证，整篇就只是讲故事。

上一版用的是 cgroup v2 的 cpu.max，思路很干净：不改频率、不改电压，只规定「每 100 ms 让你跑 X ms」。但这台机器上这条路走不通——它是 cgroup v1，而且 /sys/fs/cgroup 是只读挂载的：

mkdir /sys/fs/cgroup/cpu/wbexp → Read-only file system。容器里既不能建子组，也改不了自己的 cpu.cfs_quota_us。

于是换了一个等价做法：在同一个物理核上放 k 个空转进程，把被测进程的时间份额压到 1/(k+1)。k=0 是满份额，k=1 是 50%，k=3 是 25%。原理和配额一样——不让它跑得更慢，只让它跑得更少。

这一组把方法验证了：「吞吐腰斩」完全可以在「每 token CPU 时间不变」的情况下发生。所以 10.3 和 10.4 里没有出现的那件事（吞吐掉、每 token 时间也涨），才是真正该警惕的降频信号。

一处口径要说明：这一组的 100% 是 101.9 token/s，而 10.3 的 240 秒长跑是 102.0 token/s，两者一致；每 token 时间却差了 8.96 ms（p10）与 9.77 ms（本组用的是 getrusage 全窗口平均）。p10 与平均值不可混用，所以这一组只做内部横向比较，不跨组比绝对值。

能说的三句：

二、加核接近线性（3.91 倍），因为 32 MB 权重装得进 48 MB 的 L3。上一版的 2.24 倍是那颗芯片 L3 装不下权重导致的，不是「多线程没用」。这条修正对端侧选型影响很大：权重能不能进末级缓存，比核数更决定并行收益。

三、「变慢」和「变少」可以完全分开。份额实验里吞吐砍到 1/4，每 token 时间只涨 0.8%——这就是「变少」；间歇实验里四轮一模一样——连「变少」都没有。

不能说的三句：

一、不能说「这颗 CPU 不会热降频」。这台机器没有温度、没有频率、没有功耗，四分钟也没跑出任何热积累。诚实的说法是「在本环境、本时长内未观察到」。

二、不能把 3.91 倍外推到别的模型。32 MB 权重刚好落在 48 MB L3 之内是这份数据好看的前提；换成 7B 模型（fp16 约 14 GB），L3 一定装不下，四线程立刻退化回带宽受限。

三、不能拿绝对吞吐和上一版比。一个是 Skylake 笔记本 4 核、AVX2、双通道；一个是 Ice Lake 服务器 8 配额、AVX2（刻意避开 AVX-512）、8 通道。能比的只有「比例」和「形态」，不能比绝对值。

十一、把七组数据收成一份报告：性能、功耗、温度三栏怎么填

这一节要给出来的是一份报告，不是一堆截图。报告的价值在于：别人拿着它，能在另一台机器上复现同样的判断过程，并且知道哪些数字是测的、哪些是推的。

11.1 报告该有的六段

段落要写什么为什么必须有
一、环境能力清单哪些接口能读、哪些读不到，逐条列出决定了后面所有结论的口径，是整份报告的地基
二、被测负载定义权重多大、每 token 搬多少字节、算术强度多少没有负载定义的性能数字没有意义
三、测量方法采样方式、窗口长度、为什么用 p10让别人能判断你的数可信不可信
四、分场景数据单线程/多线程/间歇/限配额，各一组单一场景容易被误读，必须有多组互相对照
五、归因与判别用「吞吐 + CPU 时间」二维判别表给每个异常定性这是报告和截图的区别：有没有解释
六、边界声明哪些结论不能外推，换真机要改什么诚实标注边界，是这个系列从第一篇起就守的规矩

六段里，第一段和第六段最容易被省略，但它们恰恰决定了一份报告能不能被别人信任。

11.2 本机填完的样子

项目内容
内核 / 环境Ubuntu 22.04.5，内核 5.10.134-17.3.al8，Xeon Platinum 8369B（1 路 32 核 / 64 线程，L3 48 MB），cgroup 配额 8 vCPU，内存 28 GiB
被测负载32 MB 权重逐 token 全量读取，算术强度 ≈ 0.25 FLOP/字节
可读接口仅 /proc/cpuinfo（宿主采样 MHz，3400~3500 之间跳）、getrusage、cgroup v1 的配额文件（只读）
不可读接口cpufreq / thermal zone / cooling_device / powercap / MSR / perf / PSI，七路全空
核心指标每秒 token 数（吞吐）＋ 每 token 的 CPU 时间 p10（频率代理）
单线程 240 s吞吐中位 102.0 token/s，p10 中位 8.96 ms，无单调上升
四线程 180 s（4 物理核）吞吐中位 398.8 token/s，p10 中位 9.95 ms
并行效率1 → 4 线程 3.91 倍（97.8%），判定为带宽不再是瓶颈（权重可进 L3）
间歇 4 轮398.3 / 398.3 / 398.7 / 398.6 token/s，无劣化
份额 100/50/25%101.9 / 50.9 / 25.4 token/s，每 token 9768 / 9802 / 9846 μs
恢复探针864.19~864.48 Mops/s，极差 0.03%，无后遗症
一条额外发现-march=native 走 AVX-512 时每 token 25.14 ms，AVX2 只要 9.93 ms，差 2.53 倍
结论边界本环境无温度/频率通道，「未观察到降频」不可外推为「真机不会降频」

这张表就是报告的主体。注意倒数第二行——那条 AVX-512 的差是在换机器后才暴露的，它说明「同一份代码、不同编译参数」的差异，可以比「单核到四核」还大。

11.3 换到真机上，要把哪几处改掉

这份报告在云实例上完成，方法可以搬走，但有四处必须换：

环节云实例上的做法真机上该换成
读频率无接口，用每 token CPU 时间的 p10 代理scaling_cur_freq 直接读，或 turbostat 看实际频率
读温度无 thermal zone，不测thermal_zone*/temp 或 SoC 的 /sys/class/hwmon
读功耗无 powercap，不测Intel 用 RAPL（powercap/intel-rapl），ARM 用板载 PMIC/INA 电流计
制造热压力只能靠多线程加负载配合 cpufreq 限最大频、或用 stress-ng --cpu 长时间烘机
判别降频靠「吞吐↓ + p10↑」二维判别同表仍适用，但可以再加「频率↓」作为第三条证据链

方法不变，证据链从两条变三条。这也是这一篇想留下的东西：一套不依赖特权接口的判断逻辑。

11.4 三句话带走

一句话
一让 CPU 发烫的不是「算得多」，是「搬得多」——解码阶段算术强度只有 0.25 FLOP/字节，瓶颈在内存带宽，不在乘法器。
二判断「变慢」的原因，必须同时看吞吐和每 token 的 CPU 时间：只掉吞吐是抢不到时间，两个一起坏才是降频。
三功耗优化的目标不是压频率，是在给定散热条件下让每焦耳换到最多的 token；读不到的数就诚实说读不到，用代理指标推断，再用对照实验验证。

三句话都指向同一件事：先判断瓶颈在哪，再决定动哪个旋钮。判断错了，越努力越糟。
