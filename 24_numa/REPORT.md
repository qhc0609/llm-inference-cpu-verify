# NUMA 内存访问性能分析报告

**平台** openEuler 24.03 LTS-SP4 / Intel i5-7300HQ（4 vCPU / 16 GiB）/ 内核 6.12.0
**拓扑** 2 个 vNUMA 节点（`numa.vcpu.maxPerVirtualNode=2`），node0 = CPU 0-1，node1 = CPU 2-3
**数据** `results_numa/`（一轮扫描）、`results_ab/`（交替五轮）、`results_bw/`（带宽五轮）
**复算** `python3 build_med_numa.py` → `med_numa.json`

---

## 1. 结论摘要

1. 这台机器的内核拓扑是**真的**（2 节点、距离 10/20、CPU 按节点归属），但**物理链路是假的**：宿主是单路 i5，两个 vNUMA 节点背后是同一套内存控制器。
2. 因此「本地 vs 远端」的延迟差、带宽折损、互连拥塞三件事**在本机测不出来**：延迟 117.3 对 107.8 ns（远端还快 8%，区间完全重叠），decode 12.47 对 12.45 ms。
3. 能测出来的是**策略层**的三件事，而且都是硬结论：首次触碰决定页归属（33230/32769；单线程摸完全堆一边 100%）、页迁移代价（256 MiB / 57.6 ms / 4.66 GB/s）、伪共享代价（同节点 +18%，跨节点 +40%）。
4. 带宽天花板 22.3 GB/s，2 线程即到顶；decode 的权重流 21.5 GB/s = 双线程带宽的 96%，即 decode 就是一次纯带宽测试。
5. 一条可证伪的判据：**本地/远端延迟比 < 1.4 就不值得做 NUMA 调优**，先怀疑单路或虚拟化。

## 2. 环境与边界

| 项 | 值 | 备注 |
|---|---|---|
| 宿主 | Intel i5-7300HQ，1 个 NUMA 节点，4 核 4 线程，32 GiB | **单路**，这是全部限制的根源 |
| 虚机 | 4 vCPU / 16 GiB，openEuler 24.03 LTS-SP4，内核 6.12.0 | vNUMA 由 vmx 配置生成 |
| 缓存 | L1d 32 KB 8 路 / L2 256 KB 4 路 / L3 6 MB 12 路，行 64 B | 与第 18 篇同机 |
| THP | `always`（实测 `AnonHugePages` = 65536 kB，64 MiB 全部大页） | 延迟测量必须固定这一项 |
| 干扰控制 | 测量期间 `docker pause ohos-compile-env` | 该容器内有 webpack 构建，会吃满 4 核 |
| 统计口径 | 单点事实取一轮扫描；对照结论取交替五轮中位数 | 跨轮绝对值差 10%~15%，禁止跨轮比大小 |

**为什么远端测不出来**：VMware 在单路宿主上生成的 vNUMA 只复制「节点的划分」，不复制「节点间互连」。内核拿到的 `distance` 是配置值（10/20），不是硬件探测值；页被分到两个虚拟节点，但都通向同一个 DRAM 控制器。

## 3. 拓扑事实（`results_numa/topo.txt`）

| 节点 | CPU | 内存 | 距离（到 node0 / node1） |
|---|---|---|---|
| node0 | 0-1 | 7.27 GiB | 10 / 20 |
| node1 | 2-3 | 7.87 GiB | 20 / 10 |

页大小 4 KB，THP `always`。改配置前 `dmesg` 只有 `NUMA: Node 0 [mem 0x00001000-0x43fffffff]`，4 核全在 node0——即 UMA；加 `numa.vcpu.maxPerVirtualNode=2` 后变为 2 节点。

## 4. 方法：七组实验

| # | 实验 | 程序 | 输出 |
|---|---|---|---|
| 1 | 拓扑 | `19a_topo.sh` | 节点、CPU 归属、内存、距离、页大小、THP |
| 2 | 延迟矩阵 | `19b_latency.c` | 64 MiB 指针链，内存×CPU 四组合 + interleave |
| 3 | 带宽矩阵 | `13_streambw.c` | STREAM read 1/2 线程 × 四组合 + interleave；整机 1~4 线程 |
| 4 | 首次触碰 | `19c_firsttouch.c` | own / cross / single / untouched 四阶段的页落点 |
| 5 | 页迁移 | `19d_migrate.c` | 256 MiB `move_pages` 双向，含大页计数 |
| 6 | 伪共享 | `19e_share.c` | 同行 / 独占行 × 同节点 / 跨节点，2000 万次自增 |
| 7 | decode | `19f_decode.c` | 256 MiB 权重 GEMV，六种摆法 |

两个必须固定的量：延迟实验必须 `MADV_HUGEPAGE` 并回读大页数（否则 4 KB 页的 TLB 遍历会把 100 ns 变成 200~300 ns）；带宽实验必须限制线程数不超过实际可用核（`BW_MAXT`），否则「4 线程」实际是 4 线程抢 2 核。

## 5. 结果

### 5.1 延迟矩阵（64 MiB 环，THP 全覆盖）

| 内存 | CPU | ns | 单链 GB/s |
|---|---|---|---|
| node0 | node0（本地） | 109.5 | 0.58 |
| node0 | node1（远端） | 107.8 | 0.59 |
| node1 | node0（远端） | 105.4 | 0.61 |
| node1 | node1（本地） | 108.5 | 0.59 |
| interleave | node0 | 104.5 | 0.61 |

四种组合 104.5~109.5 ns，无系统性差异，且出现反向。交替五轮对照：本地中位 117.3（103.0~121.8）、远端中位 107.8（102.4~112.5），远端整个区间落在本地区间内。

### 5.2 带宽

整机 STREAM read，五轮中位数：1 线程 14.46、2 线程 **22.33**、3 线程 21.89、4 线程 21.07 GB/s。2 线程到顶，第 3、4 个线程不再增益——一套内存控制器的喂饱上限。

### 5.3 首次触碰（256 MiB）

| 阶段 | 页落 node0 / node1 | node0 占比 |
|---|---|---|
| own（4 线程各摸 1/4） | 33230 / 32769 | 50.3% |
| cross（同上，读别人的 1/4） | 33233 / 32782 | 50.3% |
| single（主线程一人摸完，绑 cpu0） | 66001 / 14 | 100.0% |
| untouched（一页不摸，直接读） | 465 / 14 | — |

`single` 就是实战中最常见的错误：单线程加载权重 → 页全堆在加载线程脚下。`untouched` 是陷阱：只分到 465 页说明读的是共享零页，带宽读数没有意义。

### 5.4 页迁移

256 MiB（65536 页，全部大页）双向：node0→node1 **57.6 ms / 4.66 GB/s**，node1→node0 **60.1 ms / 4.47 GB/s**。对照：同样 256 MiB 纯读 18.6 ms / 14.46 GB/s。迁移比纯读慢 3 倍以上——改页表、刷 TLB、对面找空闲页。

### 5.5 伪共享（2000 万次自增，2000 万×2 次操作取平均）

| 布局 | 同节点 ns/次 | 跨节点 ns/次 |
|---|---|---|
| 两个计数器同一行 | 1.57 | 1.46 |
| 各占一行（相隔 128 B） | 1.33 | 1.04 |
| 惩罚 | **+18%** | **+40%** |

跨节点时惩罚更大：一致性流量还要过互连。

### 5.6 decode（256 MiB 权重，每 token 全过一遍）

交替五轮中位数：权重 node0 12.47 ms，权重 node1 12.45 ms，2 核同在 node0 12.43 ms，1+1 跨节点 12.48 ms。权重流 21.5 GB/s，为双线程带宽的 **96%**。

## 6. 能证明 / 不能证明

| 要证明的事 | 本机 | 读数 | 真双路机典型值 |
|---|---|---|---|
| 拓扑（节点、CPU 归属、距离） | 能 | 2 节点 / 0-1 与 2-3 / 10 与 20 | 同（数字不同） |
| 首次触碰决定页归属 | 能 | 50.3% / 100% | 一致 |
| 页迁移代价 | 能 | 256 MiB / 57.6 ms / 4.66 GB/s | 同量级 |
| 伪共享代价 | 能 | +18%（同节点）/ +40%（跨节点） | 更大 |
| 带宽饱和点 | 能 | 2 线程 22.3 GB/s | 每节点一套控制器，近似翻倍 |
| 本地 vs 远端延迟差 | **测不出** | 117.3 vs 107.8 ns（反向） | 1.4~1.7× |
| 跨节点带宽折损 | **测不出** | 21.5 vs 21.5 GB/s | 本地的 60%~70% |
| 互连拥塞 | **测不出** | — | 跨节点流量互相拖慢 |

文献区间（本地 80~100 ns、跨 socket 130~160 ns、跨节点带宽 60%~70%）为公开服务器实测的常见范围，**不是本机读数**，文中与报告里均按此标注。

## 7. 工程建议

1. **先证伪**：本地/远端延迟比 < 1.4，不要做 NUMA 调优。
2. **加载阶段定落点**：先 `numactl --membind` / `--interleave` 起进程，再让加载线程待在目标节点上读权重。不要「主线程加载 → 再开多线程推理」。
3. **绑核与绑内存成对使用**：只绑一个等于白绑。
4. **三种权重摆法**：单节点常驻（模型装得下）、按节点切分（装不下且能改代码）、interleave（装不下且不想改，代价是每 token 一半流量跨节点）。
5. **别在推理循环里迁移**：一次 256 MiB 迁移 ≈ 58 ms，足够 decode 吐好几个 token。
6. **线程数不超过带宽能喂饱的核数**：本机 2 线程即到顶，第 3、4 个只是让请求互相挤。

## 8. 踩坑记录

1. **零页假带宽**：未触碰的匿名页读到共享零页。256 MiB 只分到 465 页，读数再漂亮也是假的。查 `numa_maps` 的页数，不要只看带宽。
2. **大页没拿到，延迟虚高 2~3 倍**：64 MiB / 4 KB = 16384 页，TLB 装不下，每跳多一次页表遍历。必须 `MADV_HUGEPAGE` 并回读 `AnonHugePages`。
3. **`--cpunodebind` 把「4 线程」测成 2 核**：一个节点只有 2 个核，4 个线程在 2 个核上抢。改用 `--physcpubind` 显式列出 4 个核。
4. **`move_pages` 重复迁移退化成空操作**：第二轮把页「迁」到它已经在的节点，耗时接近 0，三次取中位数会得出荒谬结果。必须每轮先无计时地迁回远端。
5. **首次触碰的聚合带宽不能用「最慢线程耗时」**：4 个 vCPU 被宿主抢占时，线程会错开几十毫秒，用单线程耗时当总时间会把带宽虚增 2~6 倍。要用逐轮墙钟 `max(end) - min(start)`。
6. **跨轮比较无效**：宿主是台笔记本，一轮一个样，绝对值差 10%~15%。所有 A/B 必须交替跑、同轮内比较。
7. **`docker pause` 不能忘**：编译容器里的 webpack 构建会吃满 4 核，让延迟从 100 ns 跳到 300 ns。

## 9. 复现

```bash
cd 24_numa
bash run_numa.sh results_numa      # 一轮扫描（七组实验）
REPS=5 bash rep.sh results_ab      # 本地/远端交替五轮
bash bw_only.sh results_bw         # 整机带宽五轮
python3 build_med_numa.py          # -> med_numa.json（本报告与文章的所有数字）
```

脚本里节点与 CPU 编号全部从 `/sys/devices/system/node/nodeN/cpulist` 读取，换到真双路机不需要改代码。

## 10. 遗留

1. 真双路机上的本地/远端延迟比、跨节点带宽折损、互连拥塞三项未测，需要一台 2P 服务器。
2. `libnuma` 的 API 级用法（`numa_alloc_onnode`、`numa_run_on_node`）未做代码示例，本文只用命令行工具。
3. mmap 加载的只读文件页（gguf）其 first touch 语义与匿名页不同，未单独做实验。
4. 未测 CPU 热迁移（`numa_balancing`）对长跑进程的影响，`/proc/sys/kernel/numa_balancing` 保持默认开启。
