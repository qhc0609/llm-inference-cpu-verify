# 19_audit —— 先量机器，再量结论

这一组不是新实验，是**审计**。

起因是一句质疑：「你要推翻的是 Windows 上测出来的数据和结论，openEuler 不可能差这么多。」
这句话是对的。操作系统换一个，不可能让 memcpy 快 65%，也不可能让 4 个线程慢 3.5 倍。
凡是出现这种量级的差异，先要怀疑的不是系统，是**测量本身**。

所以这里不写结论，先给机器立一把尺子，再拿这把尺子回头量前面 18 组实验。

## 一、先量机器

| 量什么 | 实测 | 说明 |
|---|---|---|
| 同一工作量连跑 20 次 | min 23.13 / p50 23.96 / max 26.65 ms | **极差 15.2%**（上一轮 16.7%） |
| 实际主频 | 2.03 ~ 2.13 GHz（5 次） | `/proc/cpuinfo` 死写 2496.002，是标称不是实际 |
| 透明大页 | `[always]` | 全局开启，4KB 基页 |
| steal time | 0 | 宿主没有明显抢 CPU |
| 内存 | 7430 MB，4 vCPU | i5-7300HQ，L3 6MB |

两个直接后果：

1. **这台机器上，小于 15% 的差异不构成结论。** 单次测量得到 78.8%、65%、3.5 倍这种数字，
   完全可能是同一次抖动换了个方向。
2. **按 2.5GHz 折算周期是错的，实际要按 2.05GHz。** 所以"多少次周期"这类说法整体要乘 1.2。

## 二、再量前面的结论

| 原结论 | 原值 | 复测 | 判定 |
|---|---|---|---|
| 缓存三级台阶 | 32K 1.96ns → 256M 106ns | 32K 1.632 → 256M 109.9ns | **成立**，256KB 一档两边都是 5.85ns |
| 128KB 比 256KB 还慢（组冲突） | 6.84 vs 5.85 | 3.65 vs 5.94 | **撤回**，方向相反，凹陷是噪声 |
| 只改数据顺序，分支预测 | 6.07× | 5.89× | **成立** |
| GEMM 只改循环序 | 3.3× | 3.50×（朴素 2871ms → ikj 821ms） | **成立** |
| INT4 比 FP32 慢 | 0.60× | 朴素 0.73×、查表 0.89× | **成立**（我先前把它降级，降错了，这里改回） |
| 假共享测不出 | 0.48× / 7.47× 两个反向 | 纯写 0.99×、读改写 **1.39×** | **改写**：不是测不出，是纯写测不出 |
| 线程比进程便宜，大内存会反转 | 6.72× → 0.70× | 2.72× → 5.97×（THP 开）→ **126.8×**（THP 关） | **撤回**，方向相反 |
| Attention 规模翻倍涨 6.1 倍 | 6.1× | 4.09 ~ 4.62×，n² 归一化 1.02~1.16 | **撤回**，就是标准二次 |
| 冷读比热读慢 17.6 倍 | 17.6× | 5.1×（热 7.10 GB/s，冷 1.38 GB/s） | **撤回**，量级夸大了 3 倍 |
| mmap 与堆加载 | 758MB vs 758MB | 未重测（llama.cpp 真实进程采样） | 保留 |

### 关键一条：fork 的代价由页大小决定，不由操作系统"快慢"决定

| 常驻内存 | THP 开 | THP 关 |
|---|---|---|
| 0 | 225 µs | — |
| 64 MB | 282 µs | — |
| 512 MB | 510 µs | **12969 µs** |
| 1024 MB | 786 µs | **25084 µs** |

同一台机器、同一份代码，只把透明大页关掉，fork 一张 512MB 的地址空间从 0.51ms 变成 12.97ms，
贵了 **25 倍**。原因很朴素：2MB 大页只有 256 个页表项，4KB 页有 131072 个，
fork 要复制页表并把每个 PTE 标成只读。

这才是"操作系统真能造成多大差距"的正确答案：
**不是内核跑得快慢，是内存管理策略。** 搬运数据（memcpy）开不开大页只差 1.01×，
但页表密集的操作能差 25 倍。拿这个 25 倍去解释"3 个线程慢 3.5 倍"，是拿错了武器。

## 三、为什么会错得那么离谱

三个坑，按危害排序：

1. **工作量没对齐就比时间**（13_affinity）：每线程各跑 2000 万次，4 线程干了 4 倍活，
   却拿 101.6ms 去比 28.6ms。固定总工作量后是 4.20× 加速。
2. **只跑一次就下结论**（13_affinity、03_cache）：这台机器极差 15%，单次结果没有证据力。
3. **给异常编解释**（03_cache 的"预取器接管"、p2 的"组冲突凹陷"）：现象本身是噪声，
   解释自然只能靠想象。

反过来，凡是复测后还在的结论，都有一个共同点：**效应远大于 15%**。
分支预测 5.89×、GEMM 3.50×、缓存 32K→256M 67 倍、fork 页表 25 倍。
这类东西不怕抖动；怕抖动的那些，本来就不该写成结论。

## 四、怎么重跑

```bash
scp *.c *.h run.sh root@<vm>:/root/audit/
ssh root@<vm> 'cd /root/audit && bash run.sh'
```

七个程序，全部 5~7 次取最小；`run.sh` 先打环境快照，再依次跑，结果写入 `results/`。
`audit_summary.txt` 是全部 `RES|` 行的去重汇总。

| 文件 | 做什么 |
|---|---|
| `noise_floor.c` | 20 次同一工作量 → 噪声地板；加法链估实际主频 |
| `cache_dip.c` | 64KB~320KB 每 32KB 一档，查那处"凹陷"是否稳定 |
| `quant_lut.c` | FP32 / INT8 / INT4 朴素 / INT4 查表，四种写法同台 |
| `false_share.c` | 纯写 vs 读改写，相邻 vs 填充，附并行度诊断 |
| `thread_proc.c` | 线程与 fork 在 0/64/512/1024MB 常驻下的代价，THP 开关对照 |
| `attn_scale.c` | seq 64~2048，看是不是真的 n² |
| `cold_warm.c` | 页缓存冷热、以及 THP 对纯带宽的影响 |

> 数据来自 openEuler 24.03 LTS-SP4 / 内核 6.12 / 4 vCPU（i5-7300HQ，2.05GHz 实测）/ THP=always。
> 虚拟机上的绝对值不可外推到真机，但**同一台机器内部的相对关系**是可信的，
> 前提是差异超过 15%。
