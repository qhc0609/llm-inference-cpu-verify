# 第 22 篇实验报告：CPU 算子优化，一道矩阵乘法的六次改写

**平台** openEuler 24.03 LTS-SP4（内核 6.6）/ 4 vCPU（Intel i5-7300HQ，2.5 GHz 标称，实测睿频约 3.2 GHz）/ 7.3 GiB / L1d 32 KiB per core、L2 256 KiB per core、L3 6 MiB / GCC 12.3.1
**日期** 2026-11-20
**代码** `code/22gemm.c`（约 700 行，11 个内核 + 6 种驱动模式）

---

## 一、这次要回答的问题

大模型推理里，绝大部分浮点运算花在矩阵乘法上。同一道乘法，写得好和写得差能差多少倍？差在哪一层——指令、寄存器、缓存，还是线程？

做法：固定一个 `C[MxN] = A[MxK] * B[KxN]`（fp32，行主序），写成 11 个版本，每个版本只改一个变量，全部用同一组输入、同一个参考实现校验误差，然后测量。

## 二、方法

| 项 | 做法 |
|---|---|
| 计时 | `clock_gettime(CLOCK_MONOTONIC)`，包住整次调用，含写入 C |
| 取数 | 每个配置跑 5~7 次，报「最快 / 中位 / 最慢」，正文用最快值（宿主机还跑着别的虚拟机，单次抖动可达 1.8 倍） |
| 正确性 | 每个内核的结果与 double 参考实现逐元素比对，报最大绝对误差；所有版本 ≤ 3e-6 |
| 编译 | `-O3 -mavx2 -mfma`；对照组额外加 `-fno-tree-vectorize` |
| 桌面 | 测量前 `systemctl isolate multi-user.target`，`lightdm=inactive`、load average 0.20 |
| CPU 亲和 | 单线程不绑核（绑核后观察不到改善，反而被宿主抢占时更差） |

峰值实测：10 条独立 FMA 链 × 8 lane，`102.65 GFLOPS`（单核）。按 32 flop/cycle 反推，实际频率约 3.2 GHz，比标称 2.5 GHz 高——这也解释了为什么本文所有周期类数字只能报范围。

## 三、结果

### 3.1 优化阶梯（512×512×512，单线程，最快值）

| # | 版本 | 做法 | 毫秒 | GFLOPS | 相对基线 | 最大误差 |
|---|---|---|---|---|---|---|
| 0 | naive | ijk 三重循环 | 303.42 | 0.88 | 1× | 2.7e-06 |
| 1 | ikj | 只换循环顺序 | 14.34 | 18.72 | 21.1× | 2.7e-06 |
| 2 | simd1 | 手写 AVX2 intrinsic，单累加器 | 14.74 | 18.21 | 20.5× | 2.7e-06 |
| 3 | t1 | 寄存器分块 1×8 | 35.37 | 7.59 | 8.6× | 2.7e-06 |
| 4 | t4 | 寄存器分块 4×8 | 10.37 | 25.88 | 29.2× | 2.7e-06 |
| 5 | t8 | 寄存器分块 8×8 | 6.51 | 41.20 | 46.4× | 2.7e-06 |
| 6 | asm | 手写 `vfmadd231ps` 汇编，4×8 | 9.90 | 27.11 | 30.6× | 2.7e-06 |
| 7 | block | 二级分块，默认 MC64/KC256/NC256 | 10.42 | 25.75 | 29.0× | 2.7e-06 |
| 8 | block* | 二级分块，调参 MC128/KC64/NC256 | 5.89 | 45.54 | 51.7× | 2.7e-06 |
| 9 | mt×3 | 上面的分块 + 3 线程 | 2.37 | 113.07 | 128× | 2.7e-06 |

三个反直觉的点：

1. **t1 比 ikj 还慢**（7.59 vs 18.72）。t1 是「naive + AVX2」，访问模式没改，8 个 float 一条指令只是把列跳读的问题放大了。这正好说明：SIMD 不解决访存。
2. **手写汇编没有赢**（9.90 vs 10.37，4.7%，在 1.66 倍抖动范围内）。
3. **分块默认参数不如不分块**（block 10.42 vs t8 6.51）。分块参数本身是要调的，见 3.3。

### 3.2 编译器出了多少力

| 内核 | `-fno-tree-vectorize` | 自动向量化 | 倍数 |
|---|---|---|---|
| naive | 292.31 ms / 0.92 GF | 303.42 ms / 0.88 GF | 1.0× |
| ikj | 101.12 ms / 2.65 GF | 14.34 ms / 18.72 GF | **7.1×** |
| simd1（手写 intrinsic） | 14.83 ms / 18.10 GF | 14.74 ms / 18.21 GF | 1.0× |
| t4（手写 intrinsic） | 10.01 ms / 26.81 GF | 10.37 ms / 25.88 GF | 0.97× |

`ikj` 的循环形状（连续访存、无别名、无分支）刚好是 GCC 能自动向量化的形状；手写 intrinsic 与它打平。naive 的循环形状编译器救不了——列跳读时向量化也没用。

### 3.3 Cache 分块参数扫描（1024³，单线程，3 次取最快）

60 个组合（MC∈{32,64,128} × KC∈{64,128,256,512,1024} × NC∈{64,128,256,512,1024}）：

| | MC | KC | NC | 毫秒 | GFLOPS |
|---|---|---|---|---|---|
| 最好 | 128 | 64 | 256 | 72.67 | 29.55 |
| 最差 | 32 | 1024 | 512 | 214.96 | 9.99 |

**3 倍差距，只因为三个常数**。最差点把 K 一次性走完（KC=1024），B 的面板 1024×512×4B = 2 MB 直接把 L2（256 KiB）冲爆。

### 3.4 大矩阵：分块到底救了什么（1024³，单线程）

| 版本 | 毫秒 | GFLOPS |
|---|---|---|
| t8（不分块） | 138.64 | 15.49 |
| block（默认参数） | 84.47 | 25.42 |
| block（调参） | 68.93 | 31.15 |

不分块时，B（4 MB）被每 8 行完整扫一遍，8 行一组共 128 组 → 512 MB 重复流量；MC=128 时只剩 8 组 → 32 MB。L3 只有 6 MiB，A/B/C 各 4 MB 装不下，这就是分块唯一要解决的问题。

### 3.5 算子融合（GEMM + bias + GELU）

| 形状 | K | 三趟 / 一趟（毫秒） | 收益 |
|---|---|---|---|
| 512×512 | 32 | 0.525 / 0.546 | ×0.96 |
| 512×512 | 256 | 4.453 / 4.466 | ×1.00 |
| 512×512 | 896 | 15.085 / 15.745 | ×0.96 |
| 2048×2048 | 16 | 7.790 / 5.698 | **×1.37** |
| 2048×2048 | 32 | 10.802 / 9.705 | ×1.11 |
| 2048×2048 | 64 | 22.580 / 19.938 | ×1.13 |
| 2048×2048 | 256 | 86.257 / 78.081 | ×1.11 |

512² 的 C 只有 1 MB，三趟都在 L3 里跑，融合省不到东西（反而因为 epilogue 里多一条 `vdivps` 慢 4%）。2048² 的 C 是 16 MB，两次多余的读+写是 64 MB 流量，融合才兑现。

### 3.6 多线程（1024³，默认分块，5 次取最快）

| 线程 | 1 | 2 | 3 | 4 | 6 | 8 |
|---|---|---|---|---|---|---|
| 毫秒 | 82.21 | 42.17 | 28.28 | 32.10 | 28.62 | 28.35 |
| GFLOPS | 26.12 | 50.92 | 75.93 | 66.89 | 75.02 | 75.74 |
| 加速比 | 1.00 | 1.95 | 2.91 | 2.56 | 2.87 | 2.90 |

调参后（MC128/KC64/NC256，896³）：1 线程 35.39 ms / 40.65 GFLOPS，3 线程 11.64 ms / 123.64 GFLOPS（3.04×），4 线程 14.88 ms / 96.66 GFLOPS。

**4 线程比 3 线程慢 12~25%**，和第 21 篇「4 个 vCPU 只有约 3.5 个真核」的结论一致。按行切分无锁无同步，墙钟由最慢的线程决定——只要有一个线程被宿主机换下去，另外三个 join 时都得等它。

### 3.7 低精度（Q8_0，896×896 线性层）

| M | int8 毫秒 | int8 GFLOPS | fp32 毫秒 | 相对误差（RMS） | 最大绝对误差 |
|---|---|---|---|---|---|
| 1 | 0.068 | 23.61 | 1.125 | 0.62% | 3.6e-02 |
| 16 | 1.219 | 21.07 | 0.702 | 0.65% | 3.7e-02 |
| 64 | 4.917 | 20.90 | 2.641 | 0.65% | 3.9e-02 |
| 256 | 19.535 | 21.04 | 12.710 | 0.65% | 3.9e-02 |

- **M=1（纯访存）**：16.5×。权重从 3.2 MB 降到 802 KB，字节少 4 倍；有效带宽从 2.86 提到 11.8 GB/s，又是 4 倍。
- **M=256（计算受限）**：慢 54%（19.5 ms 对 12.7 ms）。每个输出要做一次 32 字节块的横向求和，`maddubs`+`madd` 之后还要 5 条指令把 8 个 int32 收成一个标量。本机没有 AVX-VNNI（`vpdpbusd`），这个开销躲不掉，所以真正的 int8 GEMM 要按 4 行/8 列打包累加器，本文没做。

## 四、可信度边界

| 项 | 可信度 | 说明 |
|---|---|---|
| 阶梯的倍数关系（21×、51×、128×） | **A** | 同一台机、同一组输入、同一时段，比值稳定 |
| 单点 GFLOPS | **B** | 宿主机共享，单配置抖动 1.2~1.8 倍；报的是最快值，不是期望值 |
| 分块参数的相对优劣（3 倍） | **B+** | 每点只跑 3 次，但差距远大于抖动 |
| 融合收益 | **B-** | 2048²/K=16 的 1.37× 稳，其余几个点 1.05~1.13，和噪声同量级 |
| int8 的 16 倍 | **C+** | 4 倍来自字节数，另外 4 倍来自 fp32 的 M=1 路径走了标量兜底，不能全记在低精度账上 |
| NEON | **无数据** | 本机 x86_64，NEON 无法执行；正文只给指令映射与 x86 上的等价实验 |
| IPC / cache miss | **无数据** | 虚拟机 PMU 未透传（见第 21 篇），只有墙钟 |

## 五、踩坑记录

1. **`_mm256_maddubs_epi16` 的参数顺序**。第一个参数按**无符号**解释，第二个按有符号。写反了不会崩，只会算出 45 倍大的数。正确写法是先 `_mm256_sign_epi8(x, x)` 取 |x|、再 `_mm256_sign_epi8(y, x)` 取 y·sign(x)，然后 `maddubs(|x|, y·sign(x))`。
2. **融合核第一次写错**：k 分块在 tile 外层，每个 k 块都直接**覆盖** C 而不是累加，等于只算了最后一个 k 块。误差 1.638 时才被发现。改成 k 分块放在 tile 内、整条 K 走完再写回。
3. **峰值微基准一开始只有 19.8 GFLOPS**，因为 8 条链刚好卡在 FMA 延迟（4 周期 × 2 端口）的边界，循环里还有跳转开销。加到 10 条链才测出 102.65。
4. **不分块的小内核 R=1 比不加 SIMD 还慢**，一开始以为是代码写错，其实是每读一条 B 的缓存行只用 8 个 float，把列跳读放大了。
5. **`systemd-run` 直接跑脚本报 203/EXEC**，要 `/bin/bash script.sh` 包一层（第 21 篇同样踩过）。

## 六、复现

```bash
# 1. 编译（两个版本：正常 / 关闭自动向量化做对照）
gcc -O3 -mavx2 -mfma -o 22gemm 22gemm.c -lm -lpthread
gcc -O3 -mavx2 -mfma -fno-tree-vectorize -o 22gemm_novec 22gemm.c -lm -lpthread

# 2. 关桌面，跑全套（约 6 分钟）
systemctl isolate multi-user.target
bash 22run.sh

# 3. 补测调参后的配置
MC=128 KC=64 NC=256 ./22gemm bench block 1024 1024 1024 1 5 >> results22/tuned.csv
MC=128 KC=64 NC=256 ./22gemm bench mt    896  896  896  3 7 >> results22/tuned.csv

# 4. 汇总 + 出图
python3 build_med22.py      # -> med_perf22.json
python3 make_fig22.py       # -> fig22_*.png
```

所有数字都能从 `results/*.csv` 重算，正文不手写常数。
