# 17 · 真模型实测：把 Qwen2.5-0.5B 真的跑起来

前面 15 个实验都是手写 C 程序去"模拟"大模型的某一段计算。
这一组不一样：**真的加载 GGUF 权重，真的用 llama.cpp 算 token，真的让模型说话**。

目的只有一个：把前面那些微基准的结论，拿到真实推理引擎上对一遍。
对得上的留，对不上的改 —— 有几条确实对不上。

## 环境

| 项 | 值 |
|---|---|
| 系统 | openEuler 24.03 LTS-SP4（x86_64），内核 6.12.0 |
| 机器 | VMware 虚拟机，4 vCPU / 7430 MB |
| CPU | Intel Core i5-7300HQ @ 2.50 GHz（4 核 4 线程，无 SMT） |
| 指令集 | AVX2 + F16C + FMA（**没有 AVX512**） |
| 编译器 | gcc 12.3.1 |
| 推理引擎 | llama.cpp 1.0.0-dev（build 0，源码 tarball，无 git commit 可记） |
| 模型 | Qwen2.5-0.5B-Instruct，GGUF 三档：q2_k / q4_k_m / q8_0 |
| 模型来源 | ModelScope（HuggingFace 在本机不通） |

机器规格全部由 `00_env.txt` 现场采集，不是抄来的：`/proc/cpuinfo`、`nproc`、`/proc/meminfo`、`/etc/os-release`。

## 跑起来

```bash
bash 00_setup.sh          # 编译 llama.cpp + 下载三个 GGUF（需要网络）
bash run_all.sh           # 全跑，结果写 /root/llm/results
bash run_all.sh 10 30     # 只跑编号 10、30 的步骤
```

长时间运行建议放后台：

```bash
setsid nohup bash run_all.sh > /root/llm/run_all.log 2>&1 &
```

依赖：`python3`。**不需要** `/usr/bin/time`（openEuler 最小安装没有这个包，早期脚本正是栽在这里）。

## 结果

### 1. 线程扩展：预填充吃算力，解码吃带宽（q4_k_m）

| 线程 | pp512 (t/s) | 加速比 | tg128 (t/s) | 加速比 |
|---:|---:|---:|---:|---:|
| 1 | 50.60 | 1.00× | 18.14 | 1.00× |
| 2 | 99.92 | 1.97× | 32.83 | 1.81× |
| 4 | 199.79 | **3.95×** | 50.32 | **2.77×** |

4 核上预填充几乎线性（3.95×），解码只有 2.77×。
原因不是调度不好，是解码每个 token 都要把 468 MB 权重从头搬一遍，4 个核共享同一条内存总线。

### 2. 量化：省体积、涨解码、**降预填充**（4 线程）

| 档位 | 文件 | pp512 | tg128 | 困惑度 |
|---|---:|---:|---:|---:|
| q2_k | 395.9 MB | **297.15** | **61.81** | 16.10 ± 0.68 |
| q4_k_m | 468.6 MB | 193.51 | 52.21 | 15.37 ± 0.65 |
| q8_0 | 644.4 MB | 220.96 | 41.47 | **14.97 ± 0.63** |

三件事一起看才有意思：

- **解码随体积单调**：395.9 MB 比 644.4 MB 快 49%（61.81 vs 41.47），因为解码就是搬权重。
- **预填充不单调**：q2_k 最快（297），q8_0 反而比 q4_k_m 快（221 vs 194）。
  q4_k_m 的 K-quant 超级块解包指令多，在"算得多"的场景里成了瓶颈；
  q8_0 每 32 个权重一个 fp16 缩放因子，解包简单得多。**量化不只省字节，还改指令数。**
- **质量代价不对等**：q4_k_m 相对 q8_0 困惑度只涨 2.7%，q2_k 涨 7.6%。
  省一半体积只赔 2.7%，这是 q4 成为默认档的原因。

### 3. mmap 到底省了什么（q8_0，644 MB，-c 2048）

| 加载方式 | RssFile | RssAnon | 总计 | 冷启动 | 热启动 |
|---|---:|---:|---:|---:|---:|
| `--load-mode mmap` | **663.7 MB** | 94.5 MB | 758.2 MB | 1.51 s | 1.02 s |
| `--load-mode none` | 25.0 MB | **733.3 MB** | 758.3 MB | 1.64 s | 1.00 s |

**总内存几乎一模一样（758 vs 758），但性质完全不同。**

mmap 时 644 MB 权重留在文件页里 —— 内核内存紧张时可以直接丢掉，需要时再从磁盘读回；
读进堆时同样 644 MB 变成匿名页 —— 没有磁盘副本，只能写 swap 或者 OOM。
所以"mmap 省内存"这个说法不准确，准确的说法是：**mmap 把内存压力从"必须"降级成"可回收"**。

冷热差只有 0.5 s：因为模型只有 644 MB，磁盘顺序读一秒多就读完了，page cache 的收益被小模型吃掉了。
模型越大，这一栏差距越大。

顺带验到一件事：`--no-repack` 对内存没有可测影响（94.5 vs 90.4 MB 都在噪声里），
说明 repack 的副本不在这份权重的量级上，或者被 llama.cpp 复用掉了。

### 4. KV cache 是严格线性的，而且能先算出来（q4_k_m）

| 上下文 | KV cache | cells | 计算缓冲区 |
|---:|---:|---:|---:|
| 512 | 6.00 MiB | 512 | 37.77 MiB |
| 1024 | 12.00 MiB | 1024 | 38.27 MiB |
| 2048 | 24.00 MiB | 2048 | 39.27 MiB |
| 4096 | 48.00 MiB | 4096 | 41.27 MiB |
| 32768 | **384.00 MiB** | 32768 | 69.27 MiB |

每 token 固定 **12 KiB**。纸面算式：

```
24 层 × 2 个 KV 头 × 64 维 × 2（K 和 V）× 2 字节（f16） = 12,288 字节 = 12 KiB
```

和实测完全对上，误差 0。

注意最后一行：**32768 是 `llama-cli` 不加 `-c` 时的默认值**。
也就是说，什么都不设、只加载模型，KV cache 就先占掉 384 MiB ——
比 644 MB 权重的一半还多，而且全在匿名内存里。这是小机器上最容易被忽略的一块。

### 5. 上下文填得越满，解码越慢

| 已填 KV 深度 | tg128 (t/s) | 相对 d=0 |
|---:|---:|---:|
| 0 | 52.04 | — |
| 512 | 42.95 | −17.5% |
| 1024 | 41.23 | −20.8% |
| 2048 | 35.12 | −32.5% |
| 4096 | **25.61** | **−50.8%** |

深度 4096 时解码慢了一半。每次注意力都要把历史上所有 K/V 读一遍，这一段随深度线性增长，
摊到每个 token 上就体现为吞吐下滑。

对照组：`-c 256` 与 `-c 4096` 跑同一句问题，tg 是 47.6 与 46.3 t/s —— **几乎一样**。
因为 prompt 只有二十来个 token，KV 根本没填满。
**上下文上限大 ≠ 一定慢，只有真的填进去才慢**。这两组数一起看，才不会被"把 n_ctx 调小提速"这种说法骗。

### 6. 测量本身的离散度：11% ~ 15%

同一份模型、同样 4 线程，独立跑 5 次：

| 指标 | 最小 | 最大 | 极差 |
|---|---:|---:|---:|
| pp512 | 178.67 | 198.59 | **11.2%** |
| tg128 | 45.11 | 51.90 | **15.1%** |

所以本目录所有数字只在**同一数量级**上可信。
长度扫描里出现过一次 pp512 = 166.26，之后两次复测都是 195.66 / 193.38（见 `bench_pp_scan_retry*.json`），
**没有复现，按异常记录，不参与结论**。
凡是拿这台机器测出"提升了 5%"这种结论的，都不可信。

### 7. 模型真的会说话（原文照抄，不改一个标点）

`results/gen/` 下四个问题的完整输出。质量分布很不均匀，一起看：

| 问题 | 类型 | 结果 |
|---|---|---|
| L1 缓存与内存谁快 | 常识 | **胡说**。"L1 缓存是内存中的临时缓存……内存的访问速度比 L1 缓存快"，前后自相矛盾 |
| 5 亿参数 4 位量化多大 | 算术 | **算错**。写出"1GB=1024GB"、"5000000000000000000（1000 的 1000 次方）"，过程全崩 |
| 写 float 点积的 C 函数 | 代码 | **正确**。签名、循环、累加都对（多了一个没用的 `size2`） |
| 从一段说明里提取结论 | 阅读理解 | **正确**。一句话答出"靠重新排布成适合向量化乘加的分块布局" |

结论很直接：**0.5B 能把整条推理流水线跑通，速度数字是真的，但常识和算术不能当真。**
这也解释了为什么同一个模型在终端里"看起来很会说话"——生成流畅度和事实正确性是两件事。

### 8. repack 在这台机器上没测出收益

| 配置 | pp512 | tg128 |
|---|---:|---:|
| `--repack 1`（默认） | 197.83 | 50.24 |
| `--repack 0` | 195.63 | 50.33 |

差 1% 以内，落在第 6 节的离散度里。**不能据此说 repack 没用**，只能说在
"这台 CPU + q4_k_m + 0.5B" 这个组合上测不出来。想证明它有用，得换更吃带宽的配置。

## 踩过的坑（写下来省得再踩）

1. **`/usr/bin/time` 不存在**。openEuler 最小安装没装 procps 的 time，第一版脚本 12 条 RSS 全是 0.0。
   改成读 `/proc/<pid>/status` 的 `RssAnon` / `RssFile`，顺带解决了"总 RSS 分不清页类型"的问题。
   注意 `/proc/<pid>/smaps_rollup` 里**没有** RssAnon/RssFile 字段，只有 `Anonymous` 和 `Pss_*`。
2. **llama.cpp 的 JSON 字段改名了**。老版本有 `test` 和 `tps`，现在是 `n_prompt` / `n_gen` / `n_depth` + `avg_ts` / `stddev_ts`。
   按老字段取会拿到 `None`，直接 `TypeError`。
3. **`--no-mmap` 已经废弃**，换成了 `--load-mode {auto,none,mmap,mlock,mmap+mlock,dio}`。
4. **`-no-cnv` 不管用了**，现在单轮跑用 `-st`。
5. **默认上下文 32768 会把 KV 拉到 384 MiB**，做权重实验时必须显式 `-c 2048`，否则测的是 KV 不是权重。
6. **日志默认静音**。新版 llama.cpp 要加 `-v`（或 `-lv N`）才会打印 KV cache 尺寸、buffer 类型这些关键行。
7. **别让两个 bench 同时跑**。清理上一次的残留进程时，用 `pkill -f run_all` 会把自己那条 ssh 也杀掉
   （命令行里带着同样的字符串），要按 PID 杀。
8. **`curl` 拿模型比 `git clone` 靠谱**。VM 里 clone ModelScope 慢到不可用，宿主下载再传进去快得多。

## 与微基准的对照

| 微基准（手写 C） | 真模型（llama.cpp） | 是否一致 |
|---|---|---|
| 10：prefill 算力密集、decode 带宽密集 | 预填充 3.95× 线性、解码 2.77× 次线性 | 一致 |
| 09：INT4 朴素解包比 FP32 慢 | q4_k_m 预填充比 q8_0 慢 12% | 一致（解包指令是真成本） |
| 16：mmap 只是建映射，按需缺页 | 总内存不变，页类型从文件页变匿名页 | 一致，但"省内存"要改成"可回收" |
| 08：注意力随序列长度平方增长 | KV 深度 4096 时解码慢 50.8% | 一致（解码侧是线性搬运，非平方） |
| 15：线程扩展受带宽限制 | 4 核预填充 3.95×，解码 2.77× | 一致 |
| 13：绑核是负优化 | **本组未测** | 未验证 |
| 14：大小核 / EAS | **本组无法验证**（单处理器组、无 capacity） | 仍未验证 |

## 边界（必须说清楚）

- 只有 **0.5B 一个模型**。"7B 会怎样"不能从这里外推，权重体积差 14 倍，cache 行为完全不同。
- 只有 **x86 + AVX2**。没有 AVX512，所以"AVX512 一次 16 个 float"这一层完全没验到。
- **没有 GPU**。所有结论只对 CPU 后端成立。
- 困惑度用的是 llama.cpp 自带文档拼的 120 KB 语料，**只适合横向比三档量化，不能当绝对质量指标**。
- 4 个 vCPU 是宿主机分时给的，第 6 节的 11%~15% 离散度就是这件事的直接证据。
