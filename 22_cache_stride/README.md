# 22 · 步长、Cache 与访存优化：十二个实验

对应文章：《同一段代码只把步长改大一点，为什么就慢了 8 倍？》（CPU Cache 与访存优化）

这篇的原文数据是在一台 Windows Server 上量的。本目录把它整套搬到
openEuler 24.03 LTS-SP4 虚拟机上重跑一遍，**文章里的每一个数都出自这里的代码和原始日志**，
没有一个是从别处抄来或估算的。

## 环境

| 项 | 值 |
|---|---|
| 系统 | openEuler 24.03 LTS-SP4（x86_64，内核 6.12.0） |
| 形态 | VMware 虚拟机，4 vCPU |
| CPU | Intel Core i5-7300HQ @ 2.50 GHz（CPUID 报告值） |
| 内存 | 16 GiB |
| L1d | 32 KB，8 路，64 B/行，64 组（每核一份） |
| L2 | 256 KB，4 路，64 B/行（每核一份） |
| L3 | 6 MB，12 路，64 B/行（四核共享） |
| 编译器 | gcc 12.3.1，带宽类 `-O3 -march=native`，矩阵乘 `-O2` |

硬件数字不是抄表，是直接读 `/sys/devices/system/cpu/cpu0/cache/index*/`：

```bash
for i in 0 1 2 3; do d=/sys/devices/system/cpu/cpu0/cache/index$i;
  echo "$i level=$(cat $d/level) $(cat $d/type) size=$(cat $d/size) ways=$(cat $d/ways_of_associativity)"; done
```

`perf` 装了，但这台虚拟机的 vPMU 没开，`perf stat -e cache-misses` 一律返回
`<not supported>`（原始输出见 `results/perf_hw.txt`）。所以：

- 01~09、11、12 全部是**耗时与带宽的等价观测**，不掺任何计数器读数；
- 10 用**软件模型**补上缺失计数：地址序列照原样喂进一个 LRU 集相联模型
  （L1 32 KB/8 路、L2 256 KB/4 路、L3 6 MB/12 路，行 64 B），口径和 `cache-misses` 一致，
  但数它的是我们自己。模型不含硬件预取器，对循环扫描偏悲观，边界写在报告里。

完整的实验报告：[`REPORT.md`](REPORT.md)。

## 口径

1. **一次只跑一个**实验，不同时开两个，避免互相抢 CPU。
2. 每个实验内部：**先热身一遍，再正式计时三遍，取中位数**（`common.h` 里的 `median3`）。
3. 整套（01~09）**连跑五轮**，`results/s1.txt ~ s5.txt`；文章用这五轮同一档的中位数。
4. `08_gemm` 因为要换 `-O2` 单独跑，共三轮：`results/gemm_o2.txt`。
5. `09_threads` 后来又补跑五轮（`results/threads_5rounds.txt`），与前五轮合并成十轮取中位数。
6. `med.py` 就是按上面这套规则算的，输出和文章里的数字逐项对得上：

```bash
python3 med.py          # 打印成表
python3 med.py --json   # 输出 JSON（文章生成脚本读的就是它）
```

## 五个坑（都是真踩出来的）

0. **软件 miss 模型跑了七分钟不出结果**。线性探测表在大量淘汰后全是墓碑，
   一次未命中查找要扫描整张表，8M 次访问就退化到几十分钟。改成墓碑超过 2/3 时重建探测表，
   14 秒跑完。另一个坑：矩阵乘的 A 和 B 一开始用了同一段地址空间，缺失统计直接对不上，
   给 B 加矩阵偏移才正常。
1. **工作集台阶被加法器吃掉**。第一版用 64 位累加、4 个累加器，结果带宽只有 13 GB/s
   且没有台阶——瓶颈是整数加法，不是访存。改成 32 位累加（无符号回绕有定义，
   编译器敢向量化）并开 `-O3 -march=native`，台阶才出来（82.5 → 13.9 GB/s）。
2. **步长实验被依赖链吃掉**。单个 `sum += a[idx]` 是一条串行加法链，
   步长 4 B 也能测出 2.89 ns。改成 4 路展开 + 4 个独立累加器，降到 0.990 ns。
3. **冲突缺失的足迹要挑**。2 MB 足迹下 4096 B 与 4160 B 只差 1.26~1.64×，两轮还不稳定；
   `diag/diag_conflict.c` 把 32 KB~256 KB 全扫一遍，发现 256 KB 时两组分离最干净（1.81×）。
4. **矩阵分块的分块顺序不能随便写**。先写的 `i-j-k` 分块比朴素还慢；
   必须 `i-k-j`（j 最内层连续）才有用。而且**必须 `-O2`**：`-O3` 下编译器会把分块顺序重排，
   这个实验直接失效（这也是全系列唯一一个刻意降到 `-O2` 的）。
5. **手动预取在乱读上是负收益**。近距（1~16 步）全部更慢，最糟 8 步慢 1.04×；
   32 步才勉强快 1.06×。结论不是「预取没用」，而是「乱读救不回来，得先把数据排成能猜的样子」。

## 和 Windows 原文的差异（同一段代码，换了机器）

| 指标 | Windows 原文 | openEuler 本次 |
|---|---|---|
| 工作集台阶 | 5.44×（54.2 → 9.96 GB/s） | **5.96×**（82.5 → 13.85 GB/s） |
| 步长 4 B→64 B | 7.66× | **4.95×** |
| 64 MB 乱读 vs 顺读 | 203.4× | **389.3×** |
| 冲突缺失 4096 vs 4160 B | 2.40× | **1.81×** |
| AoS vs SoA | 3.76× | **3.61×** |
| 矩阵分块 | 27.7× | **3.81×** |
| 权重 / L3 容量 | 39.9×（16 MB L3） | **106.5×**（6 MB L3） |
| 4 线程伪共享 | 1.18× | **1.47×** |

方向全部一致，幅度差别不小——尤其是矩阵分块：原文那台机器算力更弱、
朴素写法更容易被内存拖死，所以分块收益显得更大。这恰恰是文章要说的：
**倍数会过期，因果不会**。

## 三条边界

1. 这是虚拟机，vCPU 靠时间片切，跨轮波动能到 ±10%。凡是 10% 以内的差别都不该当结论。
2. 4 线程聚合带宽比 3 线程还略降（20.25 → 19.39 GB/s），伪共享只测出 1.47×，
   这两处不符合教科书曲线，但都是真跑出来的，文章里照原样写了。
3. 没有 ARM 板子，也没有 vPMU，所以既没有 ARM 实测、也没有硬件计数器读数；
   这两件事在文章里都标成「公开机制 / 概念」，不冒充实测。
