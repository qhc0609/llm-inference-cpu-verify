# 计算热点与内存瓶颈定位：六个变体、一次越界、一个反直觉的绑核结论

第 25 篇配套实验。一台 4 vCPU 虚拟机上，用四个手段（向量化、绑核、分块、限频）
逐层拆解大模型推理的两个核心算子：decode 的 **GEMV** 和 prefill 的 **GEMM**。

平台：Ubuntu 24.04.5 / 4 vCPU（i5-7300HQ）/ 内核 6.8.0-149 / gcc 13.3.0 / AVX2。
**这台机器没有 vPMU**（`perf` 的 cycles、cache-misses 全部 `<not supported>`），
所以全篇不用任何硬件计数器，只用「时间 × 字节数 × FLOP」三条口径互推。

## 结论速览

| 测什么 | 关键数字 |
|---|---|
| 缓存延迟阶梯 | 4 KB **2.28 ns** → 32 KB 2.37 → 64 KB **5.51** → 256 KB 8.77 → 1 MB 27.8 → 4 MB 84.7 → 8 MB 101 → 64 MB **138 ns**（L1→L2→L3→DRAM 四段清晰） |
| 顺序带宽（8 MB / 128 MB） | 读 5.19 / 5.56，写 6.40 / 6.24，拷贝 20.10 / 17.81 GB/s |
| decode GEMV（32 MB，5 次中位） | 标量 **1.87** → AVX2 10.56 → **AVX2×4 11.27 GB/s**（**6.0×**） |
| GEMV 多线程 | 1/2/4 线程中位 8.03 / 10.06 / **9.41**——**不如单线程**，最差一次只有 4.41 |
| GEMV 绑核 | 钉 1 核 **10.14**（区间 9.06~10.72）；钉 4 核 7.72（3.19~11.94）；不钉 7.80（4.65~14.99） |
| prefill GEMM（3 次中位） | n=512：朴素 0.59 → 分块 1.27 → 2 线程 2.34 → **4 线程 4.38 GFLOPS**（**7.4×**） |
| GEMM 一致性 | 三个尺寸 × 四变体 checksum **完全相同**（按行切分不改变求和顺序） |
| GEMV 一致性 | 变体之间差在第五位有效数字（相对偏差 **4.9e-5**，在浮点重排的正常范围内） |
| 回归（连跑 10 次） | checksum 恒为 `-15572.8926`；耗时 53.87~73.33 ms，**连续分布无台阶** |

两个反直觉的地方：

1. **多线程在 decode 上一分没加，反而更不稳。** 因为 GEMV 是带宽受限的，
   AVX2×4 单线程已经跑到 11.27 GB/s，再加线程只是让四条内存流去抢同一根总线。
2. **四个线程钉在一颗核上，比散在四颗核上快 31%。** 时间片轮流跑让内存访问变成「一条整齐的顺序流」，
   预取器工作得最好；散在四颗核上是四条独立的流互相干扰。

这两条和第 23 篇（`28_sched_qos`）的结论**正好相反**——那篇测的是纯算力受限的依赖链，
结论是「4 线程钉 4 核比不钉快 14%」。两个结论都对，因为它们回答的是不同的问题。

## 一个真 bug（本仓库特意保留了修复前后的输出）

第一次跑 GEMM 时，n=256 和 n=512 的 checksum 全部一致，**只有 n=384 的 mt:4 是 700705.291**
（naive 是 560548.199，差 25%）。

| n | 每线程行数 n/4 | 块大小 BS | 是否整除 | 结果 |
|---|---|---|---|---|
| 256 | 64 | 64 | 整除 | 正确 |
| 384 | **96** | 64 | **96 = 64 + 32** | **越界** |
| 512 | 128 | 64 | 整除 | 正确 |

内层循环写的是 `i < ii + BS && i < n`，`n` 是**全局边长**而不是本线程的行上界 `t->to`。
最后那个不满 64 行的块会一直算到矩阵末尾，把后面几个线程的行又算了一遍。
修复只改一行：`i < t->to`。

- `results/secD_gemm.txt` —— 修复前（n=384 的 checksum 对不上）
- `results/secD2_gemm_fixed.txt` —— 修复后（三个尺寸全一致，n=512 mt:4 到 4.43 GFLOPS）

留着这两份，是因为「只在一个尺寸出错」这个特征在性能曲线上完全看不出来——
**如果没有顺手打 checksum，这个 bug 会被当成「多线程让 n=384 快了 3 倍」写进报告。**

## 怎么跑

```bash
cd /tmp && mkdir -p sched25/results && cd sched25
gcc -O2 -mavx2 -mfma -o hot25 hot25.c -lpthread
bash run25.sh        # 七组全跑，约 6~8 分钟
./hot25 gemv 32 avx2x4
./hot25 gemm 384 block:64
./hot25 chase 1024 30000000        # 第二个参数是总访问次数
```

`chase` 的第二个参数是**总访问次数**（内部按规模折算圈数），否则 64 MB 那档要跑好几分钟。
`gemv` 与 `gemm` 的三个变体入口都有一句 `g_touch = (float)n;`——`volatile` 写，
防止编译器把跨轮重复调用合并成一次（合并后会出现 83 GB/s 这种不可能值）。

## 边界

- 所有数字来自 x86 + AVX2。RK3588 是 4×A76 + 4×A55、用 NEON、L3 更小、带宽更低，
  但 int8/fp16 支持更好。**方向可借鉴，倍数不能照抄**（A76 的 NEON 宽度只有 AVX2 的一半）。
- 这台机器没有大小核，所以只能验证「绑核本身值多少」，验证不了「大小核该怎么选」。
- 没有 vPMU，所以没有任何「缓存命中率」数字；用的是「时间」这条最笨也最可靠的尺子。
