# 第 23 篇实验报告：CPU 调度这一层，到底能拧动多少

这份报告记录 `28_sched_qos/` 里九组实验的完整方法与全部数据。正文里每一个数字都出自
`results/sec*.txt` 的原始行，没有二次加工。

- 机器：VMware 虚拟机，4 vCPU（Intel i5-7300HQ @ 2.50 GHz），24 GB 内存
- 系统：Ubuntu 24.04.5 LTS，内核 6.8.0-149-generic（EEVDF），gcc 13.3.0
- cgroup：v2 单层级，可用控制器 `cpuset cpu io memory hugetlb pids rdma misc`
- 实时预算：`sched_rt_runtime_us=950000` / `sched_rt_period_us=1000000`，未开 `CONFIG_RT_GROUP_SCHED`
- 采集窗口：2026-11-22 10:05–10:26（宿主相对安静的一段）

## 1. 三个计时源，互相当裁判

调度这件事最容易骗人的地方是：你以为在量「等 CPU」，其实量的是「算得慢」。所以每个实验都同时拿两到三个源：

| 源 | 拿到什么 | 用在哪 |
|---|---|---|
| `CLOCK_MONOTONIC` 墙钟 | 端到端时间 | 每 token 延迟、吞吐、ping-pong 往返 |
| `/proc/self/schedstat` | 第 1 列=在 CPU 上执行；第 2 列=可运行但没轮到；第 3 列=换出次数 | A、D、K 的 `wait_pct` |
| `cpu.stat` 的 `usage_usec` | cgroup 真正消耗的 CPU 时间 | E（配额）、F（权重） |

第三种是必须的：**配额被打满时，任务不是「在 runqueue 里排队」，而是根本不被允许运行**（throttle），
`schedstat` 的第二列几乎不动，可墙钟已经翻了几倍。只用 schedstat 会得出「配额不影响调度」的错误结论。

## 2. 负载：一个最小 decode 循环

`decode <tokens> <MB>` 每次「token」做一件事：把 `MB` 大小的权重数组过一遍，做乘加，写回下沉点。
32 MB 权重、150 token：

- 单 token p50 15.74 ms，等效带宽 1.95 GB/s
- 这跟 23_membw 里单线程 read 15.89 GB/s 差 8 倍，原因是这里每次只取一个 float 做一次乘加（算术强度 0.5），
  且访问是「顺序扫一遍」但每元素只消费一次，预取器救不了乘法延迟

选择这个负载不是为了跑得快，是为了让「算」和「等」在时间上分得开：算的部分稳定在十几毫秒，
任何额外的等待都会在 `wait_pct` 上显形。

## 3. A 组：先证明「没有等待」

| 权重规模 | 每 token 中位数 | 每 token 平均 | 执行时间（150 token） | 排队等待 | 等待占比 | 等效带宽 |
|---|---|---|---|---|---|---|
| 8 MB | 3.94 ms | 4.46 ms | 659.3 ms | 0.5 ms | 0.07% | 1.79 GB/s |
| 32 MB | 15.74 ms | 16.45 ms | 2465.9 ms | 0.6 ms | 0.02% | 1.95 GB/s |
| 96 MB | 47.94 ms | 50.96 ms | 7640.2 ms | 5.2 ms | 0.07% | 1.88 GB/s |

32 MB 重复三次：等待占比 0.05% / 0.01% / 0.01%，每 token 平均 17.06 / 16.37 / 17.70 ms。

这一组的作用是**定标**：在没有竞争的情况下，调度带来的开销是千分之零点几，可以忽略。
后面所有「等待占比」的上升，都能放心归因到竞争或限制上，而不是「本来就这样」。

顺带得到一个比例：每 token 执行 16.45 ms，唤醒延迟 12.13 µs，两者差 **1356 倍**。
这就是为什么「调度优化」在 decode 场景救不了吞吐，只能救长尾——它动的是那个千分之一量级的分量。

## 4. B 组：唤醒延迟，以及策略到底改了什么

futex ping-pong：两个线程互相唤醒，测一个来回的一半，8000 次取样。

| 场景 | p50 | p99 | p99.9 | 最差一次 |
|---|---|---|---|---|
| 空闲，`SCHED_OTHER` | 12.13 µs | 13.23 µs | 14.45 µs | 202.6 µs |
| 其它核加 2 个自旋 | 12.00 µs | 12.84 µs | 158.0 µs | 0.59 ms |
| 其它核加 4 个自旋 | 12.01 µs | 12.79 µs | 204.0 µs | 70.3 ms |
| 同核 2 个自旋 | 11.62 µs | 12.81 µs | **12.24 ms** | 43.6 ms |
| 同核 3 个自旋 | 11.26 µs | 12.80 µs | **14.19 ms** | 70.2 ms |

结论一：**p50 完全不动**。哪怕同核挤了三个自旋，中位数还是 11~12 µs。
调度器把「轮到谁」的平均水平维持得很好，坏的全部在尾部。

结论二：**只有同核竞争才伤长尾**。其它核加 4 个自旋，p99.9 只到 204 µs；一旦挤到同一颗核，直接 12~14 ms，
两个数量级。这解释了为什么 cpuset 隔离比「提高优先级」更值得先做。

策略对比（同一批测量，同核 3 个自旋）：

| 策略 | 空闲 p50 | 空闲 p99.9 | 同核 3 竞争 p50 | 同核 3 竞争 p99 | 同核 3 竞争 p99.9 |
|---|---|---|---|---|---|
| `SCHED_OTHER` | 12.01 µs | 291.6 µs | 11.54 µs | 53.9 µs | 23.36 ms |
| `SCHED_BATCH` | 11.99 µs | 305.5 µs | 10.77 µs | 91.3 µs | 14.38 ms |
| `SCHED_FIFO` | 9.26 µs | 385.1 µs | 9.30 µs | 10.74 µs | **105 µs** |
| `SCHED_RR` | 9.21 µs | 460.9 µs | 9.24 µs | 10.10 µs | 98.8 µs |

同一配置的更早一批测量里，`SCHED_OTHER` 同核 3 竞争的 p99.9 是 14187 µs（见 `results/secB_wake.txt` 的 B3 段），
正文引用的是这一批。两批差 1.6 倍，是虚拟机尾部的正常抖动——**同一台机器上，p99.9 只有「数量级」可信**。

两点值得单独记：

- `SCHED_FIFO` 的 p50 比 `OTHER` 低 2.7 µs。这不是策略「更快」，而是它省掉了公平调度器挑下一个任务的记账开销。
- `SCHED_IDLE` 空载时 p99.9 只有 129 µs，看着很好；一旦同核有竞争者，p99 直接 345 ms、p99.9 **1.29 s**（补测见 `results/secB_idle_tail.txt`）。
  它把所有空档都让出去，代价是没有空档时它永远轮不上。用它做后台可以，用它做前台是灾难。

## 5. C 组：绑核与吞吐（固定总工作量）

每线程 100000 次迭代（标定为约 0.4 s），三种配置各跑 3 遍取最小值。

| 配置 | 1 线程 | 2 线程 | 4 线程 | 4 线程挤 1 核 |
|---|---|---|---|---|
| 不绑核，墙钟 | 417.8 ms | 538.5 ms | 880.7 ms | — |
| 绑定到不同核，墙钟 | 396.3 ms | 534.3 ms | 756.2 ms | — |
| 全部钉在 cpu0，墙钟 | — | — | — | 1545.5 ms |
| 等效吞吐（不绑核） | 239 千次/秒 | 371 千次/秒 | 454 千次/秒 | — |
| 等效吞吐（绑定） | 252 千次/秒 | 374 千次/秒 | 529 千次/秒 | 259 千次/秒 |

- 4 线程绑核比不绑核快 **14%**（880.7 → 756.2 ms），2 线程几乎没差别（迁移成本本来就低）
- 4 线程全挤 1 核：1545.5 ms，相当于 1.03 倍单线程吞吐——**多线程在单核上一点用都没有**，
  多出来的 8 ms 是线程切换的成本
- 4 线程相对单线程只有 1.90 / 2.10 倍，不是 4 倍：内存带宽先到顶了（这一条 23_membw 里量过）

## 6. D 组：cpuset 隔离，把「等」清零

共享 cpuset（0-3）与隔离 cpuset（2-3）各跑一遍，背景是两个自旋压在 cpu0-1。

| 配置 | 每 token 平均 | 排队等待占比 | P99 | 解读 |
|---|---|---|---|---|
| 共享 0-3，无干扰 | 17.48 ms | 0.08% | 47.4 ms | 干净基线 |
| 共享 0-3 + 2 个干扰 | 21.22 ms | **3.96%** | 119.6 ms | 开始等 CPU |
| 独占 2-3 + 同样的干扰 | 19.50 ms | **0.09%** | 158.4 ms | 等待被清零 |
| 独占 2-3，区内再加一个竞争者 | 22.93 ms | 5.45% | 167.5 ms | 隔离管不了内部 |
| 重复「独占 + 干扰」 | 18.25 ms | 0.18% | 46.7 ms | 复现性尚可 |

三个细节：

1. **等待占比能清零，P99 不能**。D3 的等待只剩 0.09%，P99 还是 158 ms（比 D2 的 119 ms 更差）。
   原因是 P99 里混着「内存带宽被隔壁抢」的成分，cpuset 只分 CPU，不分 LLC 和内存控制器。
2. **隔离只解决「别人抢我的核」，不解决「我自己人抢」**。D4 把竞争者放进同一个 cpuset，等待占比立刻回到 5.45%。
3. 这套操作要在根层先开控制器，否则写 `cpuset.cpus` 是 `EACCES`；判断是否生效必须看
   `cpuset.cpus.effective`，不是 `cpuset.cpus`。

## 7. E 组：`cpu.max` 配额，延迟变成除法

单线程 decode，`cpu.max` 依次设成 max / 100% / 50% / 25% / 10%（周期 100 ms）。

| 配额 | 每 token 平均 | 执行时间（120 token） | 排队等待 | 等待占比 | P99 |
|---|---|---|---|---|---|
| 不限 | 16.42 ms | 1973 ms | 2.1 ms | 0.10% | 20.2 ms |
| 100%（1 核） | 16.81 ms | 2022 ms | 0.6 ms | 0.03% | 44.3 ms |
| 50% | 34.29 ms | 2027 ms | 2094 ms | 50.81% | 110.5 ms |
| 25% | 69.18 ms | 2071 ms | 6227 ms | 75.04% | 170.4 ms |
| 10% | 242.45 ms | 2714 ms | 26373 ms | 90.67% | 1391 ms |

**执行时间那一列几乎是直线**：1973、2022、2027、2071、2714 毫秒。配额砍到 10%，
真正的计算只多花了 37%，而且那 37% 是节流边界的额外开销（每个周期结束时被迫让出，上下文切换变多），
不是计算变慢。每 token 从 16.4 ms 涨到 242 ms，**14.8 倍全部长在「等」上**。

这一组也解释了为什么「给推理服务定个 CPU 配额」这种做法，在延迟敏感场景非常危险：
吞吐几乎是线性可预测的，但 P99 会按 1/配额 甚至更差的比例爆掉，10% 时 P99 是 1.39 秒。

配额下的吞吐（2 线程固定工作量 120000 次迭代）：max 389.9 ms / 200% 555.9 ms / 100% 545.0 ms / 50% **1444.2 ms**。
50% 那一档正好是 100% 的 2.65 倍，比理论 2 倍更差。

## 8. F 组：`cpu.weight` 是比例，不是优先级

两个 cgroup 各跑一个自旋，**都钉在同一颗核**（cpu3），6 秒后读 `cpu.stat` 的 `usage_usec` 差值。

| 权重设置 | A 组用量 | B 组用量 | 实测比例 B/A | 理论比例 | 偏差 |
|---|---|---|---|---|---|
| 100 : 100 | 3017 ms | 3003 ms | 0.995 | 1.000 | −0.5% |
| 100 : 300 | 1703 ms | 4567 ms | 2.682 | 3.000 | −11% |
| 100 : 300（重复） | 1599 ms | 4398 ms | 2.751 | 3.000 | −8% |
| 100 : 10 | 5453 ms | 558 ms | 0.102 | 0.100 | +2% |

- 权重是**比例**：100:10 的实测比例 0.102，误差 2%；悬殊时反而更准
- 100:300 稳定偏低 8~11%：B 组拿到的 CPU 越多，它自己也越容易撞上「一个周期用满」的边界，
  真实可用时间比理论少一点
- 关键前提：两个任务必须钉在同一颗核上。第一版实验没钉核，两个任务各占一颗空闲核，
  权重完全没有作用（比例 1.00），差点被误判为「权重接口无效」

## 9. G 组：前台交互 vs 后台 AI

后台压一个 decode，前台跑 ping-pong，看后台不同优先级对前台的影响。

| 后台的优先级 | 前台 p50 | 前台 p99 | 前台 p99.9 | 前台最差一次 |
|---|---|---|---|---|
| nice 0（默认） | 8.12 µs | 12.34 µs | 288.9 µs | 7.8 ms |
| nice 10 | 11.16 µs | 12.73 µs | 9167.7 µs | 14.7 ms |
| nice 19（最低） | 12.15 µs | 12.89 µs | 2773 µs | 17.3 ms |
| `SCHED_IDLE` 后台 | 11.21 µs | 20.77 µs | 15560.9 µs | 28.0 ms |

这一组的结果和直觉相反：**nice 值调高（后台更谦让），前台的长尾并没有变好**，
nice 19 和 `SCHED_IDLE` 甚至更差。

原因是这台机器上「调低后台优先级」只改变了抢 CPU 的顺序，没有改变两件事：
后台仍然在同一个 LLC 上刷 32 MB 的数据（内存带宽照样被抢），后台被压得越狠，
它每次拿到 CPU 就越接近「把时间片用满」，反而更容易在关键时刻挤进来。
**这就是为什么给后台降优先级不是万灵药——它管得到 CPU 时间片，管不到共享缓存和内存带宽。**

## 10. H 组：饥饿，以及 RT 节流

内核参数：`sched_rt_runtime_us=950000`、`sched_rt_period_us=1000000`，即每个 1 秒周期里
实时任务最多用 950 毫秒，剩下 50 毫秒留给普通任务。`CONFIG_RT_GROUP_SCHED` 未开启。

用两个独立进程各自 `getrusage` 报账（不用线程，也不用 `CLOCK_THREAD_CPUTIME_ID`）：

| 场景 | 墙钟 | 拿到 CPU | 占比 |
|---|---|---|---|
| 普通进程独占 cpu3 | 6000 ms | 5997 ms | **99.95%** |
| 同核有 FIFO 自旋（第一次） | 6022 ms | 334 ms | **5.55%** |
| 同核有 FIFO 自旋（重复） | 6017 ms | 306 ms | **5.09%** |
| 两个实时任务抢（另一个 prio 更高） | 6000 ms | 5703 ms | 95.05% |

5.55% 和 5.09%，正好是 950/1000 留给普通任务的 5%。**实时任务并不能霸占 100%**——
只要内核开了 RT 节流（默认开），它每个周期一定会被迫让出 5%。这既保住了系统的可用性，
也意味着「用 FIFO 换低延迟」的收益上限就是那 95%。

跨 cgroup 的竞争，RT 预算也照样生效，因为没开 `RT_GROUP_SCHED` 时预算是全局的。

## 11. K 组：把手段合起来看

同一套 AI 负载（32 MB decode，120 token），背景两个自旋压在 cpu0-1。

| 配置 | 每 token 平均 | 等效吞吐 | P99 | 排队等待 | 相对「什么都不做」 |
|---|---|---|---|---|---|
| 什么都不做 | 27.81 ms | 36.0 token/s | 233.5 ms | 14.79% | 基准 |
| 只绑核（钉到 cpu3） | 25.53 ms | 39.2 token/s | 174.6 ms | 0.02% | 快 9% |
| 只做 cpuset 隔离（cpu2-3） | **20.01 ms** | **50.0 token/s** | **126.5 ms** | 0.20% | **快 39%** |
| 隔离 + 实时优先级 | 31.49 ms | 31.8 token/s | 220.4 ms | 0.01% | **慢 12%** |

最后一行是全篇最该记住的反直觉结论：**给一个长任务加实时优先级，它变慢了 12%**。
`wait_pct` 只有 0.01%（它确实没在排队），但墙钟最长。原因有两层：

1. 它一旦上 CPU 就不肯让，被 RT 节流按周期掐断（每 1000 ms 掐一次），每次掐断都要走一次完整的上下文切换
2. 它自己把两个自旋挤到「只能吃剩下的 5%」，那两个自旋反而更容易在交界处凑在一起，把内存带宽抢得更凶

**实时优先级买的是「不被别人打断」，代价是「自己打断自己」。短任务买这个划算，长任务不划算。**

## 12. 踩坑记录

这一节的每一条都真的让某一轮数据变成了废数据，写下来是为了下次别重复。

1. **ping-pong 握手序号错位，直接死锁**。一方等序号 +1，另一方等序号 -1，两边都等不到。
   现在 responder 有 500000 次空转上限，超时打印 `responder timeout` 而不是挂死。
2. **工作量太小，量到的是线程创建开销**。第一版 `work` 每线程 5000 次迭代，
   1/2/4 线程的墙钟几乎一样（全是 pthread_create 的成本）。按实测速率重标定到 100000 次（约 0.4 s）。
3. **内层循环被整段优化掉**。`for k: acc += w[k]*x[k]` 之后没有写回，编译器把整个循环删了，
   时间恒定在 0.1 ms。修法：全局 `volatile g_sink` 写回 + `wmul[k & 63]` 打破循环不变性。
4. **`g_sink` 声明写在使用之后，编译一直失败，跑的是旧二进制**。表现是「改了代码但数字一模一样」。
   最后靠 `sink=40107300.4` 这个值没变才发现。现在的做法是声明全部提到文件顶部，编译到新文件名再 `mv`。
5. **`cpuset.cpus` 写入 `EACCES`**。根层没有 `+cpuset` 时，子组的 cpuset 文件不可写。
   必须先 `echo "+cpu +cpuset" > /sys/fs/cgroup/cgroup.subtree_control`。
6. **F 组第一版设计错了**：两个任务没钉核，各自跑在空闲核上，权重自然无效。
   修法：两个 cgroup 都 `cpuset.cpus=3`，再读 `cpu.stat` 的 `usage_usec` 差值。
7. **饥饿实验口径全错**。第一版用线程，把各线程的 CPU 时间相加，结果超过墙钟（线程组统计会重复计）；
   换 `/proc/self/schedstat` 读不到；换 `CLOCK_THREAD_CPUTIME_ID` 在切换时不可靠。
   最终方案：起两个**独立进程**，各自 `getrusage(RUSAGE_SELF)`，误差立刻消失。
8. **`SCHED_IDLE` 同核 p99 最初是编的占位值**。图已经画好了但那一格没测，先填了个「约 300 ms」。
   后来补测，真实值是 345 ms / p99.9 1.29 s，与占位值巧合接近，但性质完全不同——占位值不能被当成数据。
9. **`run23.sh` 用 CRLF 存盘，建出一个叫 `results\r` 的目录**。表现是「跑完了但结果目录是空的」。
   仓库里的脚本一律 LF。

## 13. 可信度边界

- **微秒级数字只看分布**。宿主机是共享的 4 核，p99.9 在两次运行之间能差 1.6 倍。
  本报告所有 p99.9 都只当「数量级」用。
- **没有 vPMU，拿不到 IPC 和 cache miss**。所以「为什么慢」只能靠时间差和带宽反推，
  不能直接看硬件计数器。相关的能力边界见 `26_perf/`。
- **4 个核完全对称，没有 big.LITTLE/EAS**。本目录不涉及大小核调度。
- **`results/rerun_busy/` 是一次反例**。同一天宿主较忙时重跑，「什么都不做 / 只绑核 / 只隔离」的排序发生反转
  （K1 24.46 ms、K2 25.24 ms、K3 26.84 ms，隔离反而最慢）。这不是代码变了，
  而是背景噪声把 3~7 ms 的差距淹掉了。**虚拟机上的单次横向对比不可信**，正文的结论建立在
  同一窗口内多次重复、且方向一致的那些项上。
- **配额的「执行时间不变」有前提**：任务在 100 ms 周期内能用完自己的配额，且不涉及跨核迁移。
  周期设得很短（比如 1 ms）时，节流开销会显著上升，那一档没有测。
