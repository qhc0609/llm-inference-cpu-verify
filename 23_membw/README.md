# 23 · 内存带宽与 CPU 瓶颈：五个实验加一张屋顶线

对应《同样四个核，为什么「一个字一个字往外吐」时只剩 1/93 的算力？》。
所有数字都是本机 openEuler 虚拟机真跑的，原始 `RES|` 日志在 `results/`。

| 实验 | 量什么 | 关键数字 |
|---|---|---|
| `13_streambw.c` | read / copy / scale / triad，单线程与 1–4 线程 | 单线程 read **15.89 GB/s**（纸面 38.4 的 41%）；copy 13.57；4 线程 23.17 反而低于 2 线程 24.50 |
| `14_latency_mlp.c` | 128 MiB 随机环，同时追 1–32 条指针链 | 延迟 109.7 → 134.4 ns 几乎不变，带宽 0.58 → 3.81 GB/s（**6.52×**）；16 链之后只增延迟 |
| `15_peakflops.c` | 1 累加器 / 8 累加器，单线程 / 四线程 | 10.65 / **87.21** / **345.66** GFLOPS；ILP 收益 8.19× |
| `16_ai_sweep.c` | 算术强度 0.5 → 64 扫描 | 7.81 → 82.02 GFLOPS，实测弯折在 AI 8–32 |
| `17_batch.c` | batch 1 → 256，8×8 寄存器分块 | 每 token 9.06 → **1.11 ms**（8.16×），AI 0.5 → 113.8 |

由 13 与 15 得到这台机器的两条边：

- 单线程：`y = min(87.21, 15.89 × AI)`，屋脊点 **AI = 5.49**
- 四线程：`y = min(345.66, 23.17 × AI)`，屋脊点 **AI = 14.92**

## 踩过的坑

0. **`16_ai_sweep` 的高 AI 档算出 222 GFLOPS**，比单线程峰值 87 还高，一看就是错的。
   原因是 `bench(R, reps)` 里两个参数打架：`R = 32` 却走了 `reps == 4` 的分支，只做了 4 个 FMA。
   改成只按 `R` 分支、`reps = R / 8` 才对上。
1. **`17_batch` 的循环顺序改了两版**。第一版 `k-j-b`，C 按 16 KB 跨步访问，B = 256 只有
   0.28 GFLOPS（全是冲突缺失）；第二版把 b 放到外层，又把 64 MB 权重重读了 256 遍。
   最终按 `jb / kb` 分块让 128 KB 权重块留在 L2，内层 8×8 寄存器分块，才到 30 GFLOPS。
2. **16 / 32 条链的带宽停在 4.2 GB/s**，一开始怀疑 TLB：128 MB 随机漫步每两次就缺一次页表项。
   查了 `/sys/kernel/mm/transparent_hugepage/enabled` 发现已经是 `always`（AnonHugePages 2.4 GB），
   排除大页问题，确认是 DRAM 行激活——随机 64 B 访问只能到顺序读的 26%。
3. **4 线程带宽低于 2 线程**（23.17 对 24.50）。这台虚拟机只有 4 个 vCPU，物理核还要和宿主分享，
   线程一多调度抖动就吃掉收益。不是测量错误，如实记录。

## 与板子的关系

本机是 x86 虚拟机 + DDR4，没有 RK3588、没有 LPDDR 控制器。所以：

- LPDDR 的带宽只在文章里按「数据率 × 位宽 ÷ 8」推算，标明是规格推算；
- 这五个基准只依赖 `clock_gettime` 和 `pthread`，换到板子上跑同样的命令就能得到同一张屋顶线。
